# Egypt Supermarket POS — وثيقة المتطلبات والمواصفات الهندسية الموحدة

**الإصدار:** `v1.0-consolidated`  
**التاريخ:** 12 نوفمبر 2026  
**المنتج:** برنامج نقاط البيع وإدارة السوبرماركت للسوق المصري  
**المستودع المقترح:** `egypt-supermarket-pos` (مستقل عن مشاريع المطاعم والكافيه)  
**الهدف:** مرجع واحد لكتابة كود إنتاجي متدرج يمكن اختباره وتسليمه، وليس واجهات شكلية.  
**الحالة:** **مسودة تنفيذ هندسي محسّنة** تجمع الوثيقتين؛ القرارات المفتوحة وقيود الامتثال **ليست معتمدة تلقائيًا**.  
**الملفات المصدر:** `وثيقة المتطلبات والمواصفات الهندسية النهائية(1).md` و`egypt_supermarket_pos_final_spec(1).md`.

> **مبدأ حاكم:** بنود العمل المعتمدة محفوظة، أما اختيار المكتبة/طريقة التنفيذ/السياسة القانونية التي لم تثبت بتجربة أو موافقة فتوضع في سجل قرارات. لا يتحول أي "مقترح" إلى قاعدة إنتاجية دون توثيق واعتماد.

## كيفية استخدام الوثيقة

- **المعتمد تجاريًا (BR):** يلزم المنتج: Windows وAndroid، العمل داخل الفرع دون إنترنت خارجي، شبكة محلية متعددة الأجهزة، الفروع، الأنظمة المالية والمخزنية، تجهيز الأصناف، الترخيص السنوي 500 جنيه مصري لكل جهاز، النسخ اليومي، العربية والإنجليزية، وواجهة مبسطة.
- **القواعد الهندسية الأساسية (ENG):** معاملات ذرية، سجلات مالية ومخزنية قابلة للتدقيق، منع التكرار، حدود تفويض، استعادة النسخ، حماية الأسرار؛ تُراجع تفاصيل التنفيذ دون التخلي عن الضمان.
- **قرار يحتاج اعتمادًا (DEC):** خدمة السحابة، طريقة حساب التكلفة في حالات خاصة، أجهزة البيع المدعومة، سياسة المزامنة المفصلة، تفاصيل الضريبة والتراخيص، ونحوها.
- **قيد قانوني (LEGAL):** أي حُكم عن الضرائب أو صلاحية بيع الغذاء يخضع للتحقق من المتطلبات المصرية الرسمية السارية وقت النشر، ولا يثبت بهذه الوثيقة وحدها.
- **اختبار قبول (AT):** لا تُعد الميزة منجزة إلا بعملها على البيانات الحقيقية/الاختبارية المصطنعة وعرض نتيجة الاختبار والسجلات ذات الصلة.

## نطاق الإصدار الأول

**داخل النطاق النهائي للإصدار الأول:** إدارة المنشأة والفروع، المخازن، العملاء والموردون، الأصناف والوحدات والباركود، الشراء والمبيعات والمرتجعات، الدفع المختلط والآجل، المخزون والتشغيلات والتجهيز والفاقد، جرد حي، الخزينة والورديات، تقارير وأرباح تقديرية، صلاحيات وترخيص، نسخ احتياطي، طباعة، مزامنة الإدارة الرئيسية، وواجهات Windows/Android. بعض هذه الوحدات تُسلّم على مراحل متتابعة ولا تُعتبر متاحة فور الانتهاء من المرحلة الأولى.

**خارج النطاق حتى قرار مستقل:** المطاعم/الكافيهات، أنظمة رواتب مؤسسية معقدة، نقاط ولاء وتسويق متقدم، متجر إلكتروني، تكامل بوابات دفع بنكية مباشرة، تكامل ضريبي رسمي قبل التحقق والتسجيل والتصديق، وأجهزة لم يتم اختبارها.

## تسلسل الأولوية المطلوب

1. حفظ العمليات والأرصدة دون فقد أو تكرار، ثم أمن الصلاحيات.
2. عمل الفرع محليًا باستقلال عن الإنترنت، وسلامة المعاملات تحت عدة كاشيرات.
3. بيع وشراء ومخزون وتكلفة وديون يمكن مطابقتها مع الدفاتر.
4. سرعة UX للكاشير وتجهيز الأصناف والميزان والجرد.
5. الفروع والتقارير والتراخيص والنسخ الاحتياطية ومعايير الإصدار.

# 1. تعليمات أساسية وحاسمة إلى Anti-gravity

1. المطلوب بناء برنامج تجاري فعلي (Production-Grade Commercial Software)، وليس نموذجًا تجريبيًا (Prototype) أو واجهات شكلية (Mockups).
2. اقرأ الوثيقة كاملة؛ صمّم عقد البيانات المنطقي للمنظومة كلها منذ البداية، ونفّذ جداول المرحلة الحالية بترحيلات تدريجية، وأسّس خدمة الخادم المحلي ومسار العمليات من المرحلة الأولى.
3. لا تحذف أو تختصر أي متطلب دون توضيح السبب وطلب الموافقة الصريحة.
4. لا تضع بيانات تجريبية صلبة (Hardcoded Dummy Data) على أنها بيانات حقيقية في الكود التنفيذي.
5. يجب أن تؤثر كل عملية داخل معاملات ذرية (ACID Database Transactions) في قاعدة البيانات والأرصدة والتقارير ذات الصلة؛ لا تنشئ أزرارًا شكلية.
6. اربط البيع بالمخزون والخزينة وحساب العميل، والشراء بالمخزون وحساب المورد والخزينة.
7. لا تعرض لصاحب النشاط شجرة حسابات أو قيودًا يومية أو دفتر أستاذ أو ميزان مراجعة. المطلوب **محرك حسابات داخلي مزدوج القيد ودقيق (Internal Double-Entry Ledger Engine)** يعمل في الخلفية بواجهة تشغيلية مبسطة تمامًا للمستخدم.
8. منتج السوبرماركت مستقل تمامًا عن مشروعي الكافيه والمطاعم المستقبليين: مستودع GitHub مستقل، وقاعدة بيانات مستقلة، ومنطق عمل مستقل، وإعدادات وترخيص مستقل.
9. لا تعتبر الميزة مكتملة لمجرد ظهور الشاشة؛ يجب تنفيذ منطقها البرمجي (Domain Logic) وربطها بقاعدة البيانات والخادم المحلي واختبارها وحفظ بياناتها.
10. صمّم نموذج بيانات قابلًا لدعم المتطلبات الضريبية المصرية وتكامل الفاتورة/الإيصال الإلكتروني، لكن **لا تدّعِ الامتثال القانوني أو تفعّل تكاملًا رسميًا** قبل التحقق من المواصفات الرسمية السارية، وحالة تسجيل المنشأة، والتجارب والاعتمادات اللازمة. فرّق في الواجهة بين الفواتير الداخلية وبين المستندات المتكاملة رسميًا.

# 2. الهدف ونطاق المنتج

بناء برنامج POS وإدارة سوبرماركت باللغة العربية والإنجليزية، يعمل على Windows وAndroid، ويدعم العمل دون إنترنت (Offline-First)، وجهازًا واحدًا أو عدة أجهزة عبر شبكة محلية (LAN)، مع دعم الفروع والمزامنة المركزية من الإصدار الأول.

البرنامج موجه لصاحب سوبرماركت يدير نشاطه دون محاسب متخصص. يجب أن تكون العمليات اليومية بسيطة وسريعة، بينما يحسب النظام تلقائيًا المخزون والتكلفة والربح والمديونيات وحركة النقدية.

## 2.1 استقلال بيانات المنشأة (Multi-Tenant Isolation)

- كل منشأة (`Tenant`) لها معرف فريد `tenant_id` وقاعدة بيانات وإعدادات وترخيص مستقل.
- يمكن تثبيت المنتج نفسه لدى عدة سوبرماركت، مع فصل بيانات كل منشأة تمامًا.
- تغيير اسم المنشأة أو شعارها أو بياناتها لا يغير الفواتير التاريخية.
- تحفظ الفاتورة المعتمدة لقطة ثابتة غير قابلة للتعديل (`Immutable JSON/Column Snapshot`) من بيانات المنشأة والعميل والأصناف والأسعار والضرائب وقت الإصدار.
- لا يسمح بتسرب البيانات بين منشأتين أو فروع غير مصرح بها.

## 2.2 المنصات والأجهزة

- **Windows:** جهاز رئيسي للفرع (يعمل كمحطة كاشير/إدارة + خادم فرع محلي) وأجهزة Windows إضافية.
- **Android:** هواتف وأجهزة لوحية (كاشير متنقل، جرد، استلام بضاعة، لوحة مالك) متصلة بشبكة الفرع أو بالإدارة المركزية.
- واجهة متجاوبة (Responsive & Adaptive) مع أحجام الشاشات المختلفة.
- دعم قارئ باركود (USB HID / Serial)، وطابعات حرارية (ESC/POS عبر USB / Ethernet / Bluetooth)، وطابعات ملصقات الباركود، وموازين إلكترونية عبر طبقة تعريف قياسية (Hardware Abstraction Layer).

# 3. الفروع والبنية التشغيلية -- من الإصدار الأول

## 3.1 هيكل كل فرع ومعمارية الاتصال المحلي (LAN Architecture)

- كل فرع له جهاز Windows رئيسي يعمل كخادم محلي (`Local Branch Host Server` مبني بـ `Dart Shelf`)، وقاعدة بيانات `SQLite` محلية مستقلة تعمل في وضع `WAL Mode` (Write-Ahead Logging) لضمان الأداء العالي وعدم قفل القراءة أثناء الكتابة.
- **قاعدة معمارية صارمة:** حتى على جهاز Windows الرئيسي نفسه، يتعامل تطبيق الواجهة مع قاعدة البيانات عبر طبقة مستودعات موحدة (`Unified Repository Layer`) تدعم العمل المباشر أو عبر API المحلية، ويُمنع منعًا باتًا فتح ملف `SQLite` مشترك عبر مجلد شبكة (SMB/Shared Folder) من عدة أجهزة.
- تتصل أجهزة الفرع الإضافية (Windows وAndroid) بالخادم المحلي عبر شبكة Wi-Fi أو Ethernet بواسطة REST API + WebSockets (لتحديث الشاشات لحظيًا) مع توثيق الاتصال عبر رمز أمان محلي (`JWT / Branch Secret`).
- **اكتشاف الخادم المحلي والربط السريع:**
  1. يبث خادم الفرع على Windows خدمته تلقائيًا في الشبكة المحلية عبر بروتوكول `mDNS / Bonjour`.
  2. يعرض خادم Windows شاشة **"ربط جهاز جديد عبر QR Code"** تحتوي على (عنوان IP المحلي، المنفذ Port، معرف الفرع، ومفتاح الإقران الآمن)، بحيث يمسح هاتف Android الرمز للاتصال الفوري دون إدخال تقني معقد، مع إتاحة الإدخال اليدوي للـ IP كبديل احتياطي.

## 3.2 الإدارة الرئيسية والمزامنة السحابية (Cloud Sync & Conflict Resolution)

- إدارة رئيسية تعرض بيانات الفروع المصرح بها وتقاريرها المجمعة، مع اختيار وسيلة الربط المركزي (مثل **PostgreSQL / Supabase أو استضافة ذاتية**) أثناء قرار معماري موثق، بعد قياس التكلفة والاعتمادية والأمان ومتطلبات نشر بيانات كل منشأة؛ لا يُفترض أنها مجانية دائمًا.
- كل فرع يستمر بالبيع محليًا عند انقطاع **الإنترنت الخارجي** ما دام خادم الفرع المحلي وشبكته وأجهزته التشغيلية متاحة؛ أما انقطاع جهاز كاشير فرعي عن خادم الفرع فهو فشل مختلف له سياسة مستقلة.
- عند عودة الاتصال، تتم المزامنة تلقائيًا في الخلفية وبشكل آمن عبر طابور مزامنة دائم (`Persistent Outbox/Inbox Sync Queue`).
- **قواعد المزامنة ومنع التعارض (Idempotent Event-Driven Sync):**
  - لا تتم المزامنة بنسخ قاعدة بيانات فرع فوق قاعدة بيانات فرع آخر.
  - لكل عملية معرف فريد مرتب زمنيًا `UUIDv7`، ومعرف منشأة `tenant_id`، ومعرف فرع `branch_id`، ومعرف جهاز `device_id`، وتوقيت منطقي هجين (`Hybrid Logical Clock - HLC`)، ومفتاح عدم تكرار (`Idempotency Key`).
  - **العمليات المالية والمخزنية (المبيعات، المشتريات، التحصيلات، المدفوعات، حركات المخزون):** تُزامن كسجل حركات إضافي غير قابل للمسح (`Append-Only Ledger Events`). لا تُستخدم قاعدة "آخر تعديل يفوز" (`Last-Write-Wins`) أبدًا في الأرصدة المالية أو المخزنية، بل يُحسب الرصيد من مجموع الحركات المعتمدة.
  - **بيانات الكتالوج والإعدادات (أسماء الأصناف، الباركود، التصنيفات):** تُدار مركزيًا من المالك وتُعمم على الفروع، مع السماح بتخصيص (`Branch Override`) لسعر البيع والحد الأدنى للطلب وموقع الرف على مستوى كل فرع.
- تحويل المخزون بين فرعين يسجل حركة **"إرسال بضاعة بالطريق (In-Transit Out)"** في الفرع المصدر (تخصم من المتاح في المصدر فورًا)، وحركة **"استلام بضاعة محولة"** في الفرع المستلم. لا تصبح الكمية متاحة للبيع في الفرع المستلم إلا بعد تأكيد الاستلام، مع معالجة فروق الاستلام (نقص/تالف أثناء النقل) بمحضر تسوية موثق.
- إظهار حالة المزامنة بوضوح في الشريط العلوي: متصل، غير متصل، عدد العمليات التي تنتظر المزامنة، فشل المزامنة (مع السبب)، وتاريخ/وقت آخر مزامنة ناجحة.
- عند انقطاع الشبكة المحلية بين جهاز كاشير فرعي والخادم المحلي: **لا يعلن الجهاز نجاح بيعٍ لم يثبته خادم الفرع**. في النسخة الأولى يحفظ السلة كمسودة محلية آمنة (دون إنقاص المخزون أو تحصيل معتمد) ويمنع الاعتماد النهائي حتى عودة الاتصال؛ أي وضع بيع مستقل على الجهاز يحتاج قرارًا وتصميمًا إضافيًا لمنع بيع المخزون نفسه مرتين. تُستخدم مفاتيح عدم التكرار عند الإعادة.

## 3.3 إدارة الفروع والمخازن الفرعية

- يتضمن الإصدار الأول: إضافة وتعديل وإيقاف فرع؛ اسم الفرع وعنوانه وبيانات الاتصال ومديره.
- **دعم تعدد مواقع التخزين داخل الفرع الواحد:** كل فرع يحتوي افتراضيًا على "صالة العرض (Sales Floor)" مع إمكانية إضافة "مخزن خلفي (Backroom Warehouse)" أو أكثر تابع لنفس الفرع، لتحويل البضاعة داخليًا أو الجرد المنفصل.
- مخزون مستقل وأسعار قابلة للتوحيد أو الاختلاف حسب الفرع.
- خزينة وورديات مستقلة لكل فرع.
- مشتريات وموردون ومديونيات مرتبطة بالفرع أو مشتركة على مستوى المنشأة وفق إعداد المالك.
- ترقيم فواتير منظم ومستقل لكل فرع وجهاز دون أي تصادم، بالصيغة القياسية:  
  `[BranchCode]-[DeviceCode]-[Year]-[SequenceNumber]` (مثال: `BR01-POS2-2026-0000145`).

# 4. التصميم وتجربة الاستخدام (UI/UX)

- تصميم عصري وفخم واحترافي، هادئ وواضح، بعيد عن شكل برامج الكاشير القديمة المزدحمة.
- ألوان متناسقة وهادئة مع تباين قياسي واضح (WCAG AA)، وأيقونات واضحة وموحدة، وخطوط عربية مريحة عالية الوضوح (مثل `Cairo` أو `IBM Plex Sans Arabic`).
- دعم الوضع الفاتح (Light Mode) والداكن (Dark Mode).
- دعم العربية `RTL` والإنجليزية `LTR` في الشاشات والتقارير والفواتير.
- **ضبط اتجاه الأرقام والرموز:** فرض عرض الأرقام والأسعار والباركود والتواريخ باتجاه قراءة صحيح (`LTR` داخل حاويات `RTL` عند اللزوم) لمنع انعكاس علامات السالب أو الكسور العشرية أو العملة.
- واجهات مناسبة للمس (Touch-Friendly) بأزرار لا تقل أبعاد منطقة اللمس فيها عن $48 \times 48\text{ px}$ في شاشة الكاشير.
- دعم كامل للوحة المفاتيح والاختصارات السريعة للكاشير (`F1` بحث، `F2` تغيير الكمية، `F4` تعليق فاتورة، `F5` دفع نقدي سريع، `F9` اعتماد وطباعة، `ESC` إلغاء).
- قوائم منظمة وبحث ذكي فوري بالباركود والاسم والكود، ورسائل أخطاء عربية مفهومة؛ يُضبط هدف الأداء بالقياس على عتاد مستهدف (هدف طموح: `p95 <= 50ms` للبحث المحلي الدافئ دون زمن طباعة/شبكة).

# 5. ملف المنشأة

يدعم الاسم التجاري والاسم القانوني إن وجد، الشعار، اسم المالك ونوع النشاط، الدولة (مصر افتراضيًا)، المحافظة والمدينة/المركز والمنطقة والعنوان التفصيلي، أرقام الهواتف والبريد الإلكتروني والموقع الإلكتروني اختياريًا، الرقم/التسجيل الضريبي (9 أرقام بتحقق صحتها) وحالة التسجيل الضريبي، رقم السجل التجاري وبيانات رسمية إضافية قابلة للتخصيص، العملة الافتراضية الجنيه المصري (`EGP`)، اللغة والتاريخ والوقت والمنطقة الزمنية (`Africa/Cairo`)، إعدادات الطباعة والفواتير والضرائب، وبيانات التواصل مع الدعم الفني.

تعديل بيانات المنشأة يطبق على الفواتير الجديدة فقط ولا يغير المستندات التاريخية المعتمدة.

# 6. المستخدمون والصلاحيات والأمان

## 6.1 الأدوار الافتراضية

المالك (Super Admin)، مدير الفرع، الكاشير، مسؤول المخزن، مسؤول المشتريات، مع إمكانية إنشاء أدوار مخصصة (Custom Roles).

## 6.2 الصلاحيات التفصيلية (RBAC + Scope Control)

يحدد المالك لكل مستخدم صلاحيات دقيقة تشمل:
- عرض أو إخفاء تكلفة الشراء وهامش الربح وصافي الأرباح.
- إنشاء أو تعديل أو إيقاف صنف.
- تعديل الأسعار والعروض.
- تطبيق خصم ضمن سقف محدد (نسبة أو مبلغ) أو تجاوز الحد الأدنى للسعر (يتطلب رمز PIN أو بصمة/كلمة مرور المدير على نفس الشاشة - **Supervisor Override Modal**).
- إلغاء بند بعد إضافته في شاشة الكاشير، أو إلغاء فاتورة معلقة، أو تنفيذ/اعتماد مرتجع.
- إدخال أو اعتماد جرد مخزني.
- تسجيل تالف أو هالك أو استهلاك داخلي.
- تسجيل مصروف أو دفعة مورد أو تحصيل عميل.
- فتح درج النقدية دون بيع وفتح/إغلاق وردية، واختيار هل الإغلاق **"إغلاق أعمى (Blind Close)"** (يُدخل الكاشير النقدية الفعلية دون أن يرى المبلغ المتوقع لمنع التلاعب) أم إغلاق عادي حسب سياسة المالك.
- عرض تقارير فرع محدد أو جميع الفروع.
- إدارة المستخدمين والإعدادات والتراخيص، وتصدير البيانات أو استعادة نسخة احتياطية.

## 6.3 لوحات التحكم حسب الدور

- **لوحة المالك:** جميع الفروع أو فرع محدد، المبيعات والأرباح التقديرية، المصروفات، الخزائن، ديون العملاء ومستحقات الموردين، قيمة المخزون بالتكلفة والبيع، النواقص والراكد، تنبيهات الصلاحية، أداء الفروع والموظفين، التقارير والإعدادات والتراخيص وحالة النسخ الاحتياطي.
- **لوحة المدير:** بيانات الفروع المصرح بها، المبيعات والورديات، المنتجات والأسعار والعروض، المخزون والمشتريات، العملاء والموردون، المصروفات وفق الصلاحية، اعتماد العمليات المعلقة والتقارير.
- **لوحة الكاشير:** البيع السريع، البحث بالباركود والاسم، تعليق واستكمال الفواتير، تسجيل الدفع والطباعة، المرتجعات إذا سمحت الصلاحية، فتح وإغلاق الوردية. لا يرى تكلفة الشراء أو الأرباح أو حسابات الموردين افتراضيًا.
- **لوحة مسؤول المخزن:** استلام وإدخال البضاعة، الأرصدة ومواقع التخزين، الجرد والتالف، التشغيلات والصلاحية، التجهيز والتعبئة وطباعة الملصقات، والتحويلات المخزنية وفق الصلاحيات.

## 6.4 سجل التدقيق الأمني (Immutable Audit Log)

- يسجل النظام تلقائيًا: من قام بالعملية، الفرع والجهاز، نوع العملية، التاريخ والوقت، القيم قبل وبعد بصيغة JSON في التعديلات الحساسة (تغيير سعر، خصم، إلغاء بند، تعديل كمية، جرد)، وسبب الإلغاء أو التعديل، والمشرف الذي اعتمد التجاوز إن وجد.
- لا تحذف الحركات المالية أو المخزنية المعتمدة حذفًا نهائيًا (`Hard Delete` ممنوع تمامًا على جداول الحركات)؛ يُستخدم الإلغاء الموثق أو الحركة العكسية (`Reversal Entry`).

# 7. المنتجات والأصناف والوحدات والباركود

## 7.1 بطاقة الصنف

- اسم عربي (إجباري) واسم إنجليزي (اختياري) وصورة اختيارية مضغوطة.
- كود داخلي `SKU`، وكود ميزان `Scale PLU` (مكون من 5 أرقام للأصناف الموزونة).
- باركود واحد أو عدة باركودات لنفس الصنف والوحدة (`Multi-Barcode per Unit`).
- التصنيف، القسم، العلامة التجارية، والمورد الافتراضي.
- **نظام الوحدات الهرمي (Multi-UOM Conversion):** وحدة الأساس الصغرى لحفظ المخزون (مثل: قطعة، جرام، مل)، مع وحدات كبرى للشراء أو البيع بمعامل تحويل دقيق (مثال: كرتونة $= 24$ علبة، علبة $= 12$ قطعة؛ أو شيكارة $= 25,000$ جرام). لكل وحدة باركود مستقل وسعر بيع خاص بها.
- سعر الشراء الأخير، والمتوسط المرجح للتكلفة (`WAC`)، وسعر قطاعي، وسعر جملة، وأسعار خاصة، والحد الأدنى المسموح به لسعر البيع.
- حد إعادة الطلب (Reorder Level) والحد الأعلى للمخزون.
- **الإعدادات الضريبية:** نوع الضريبة أو الإعفاء، ونوع الكود الضريبي القياسي (`GS1` أو `EGS`) ورقم الكود الضريبي للصنف (لدعم الربط الضريبي المصري عند تفعيله).
- سياسة التتبع: بدون تتبع تشغيلة، أو تتبع التشغيلة وتاريخ الصلاحية، أو صنف خام قابل للتجهيز والتقسيم، أو صنف ناتج عن تجهيز.
- حالة الصنف (نشط / موقوف عن الشراء / موقوف كليًا)، وموقع الرف أو المخزن، وسجل تاريخ تغير الأسعار والتكلفة.

## 7.2 أنواع المنتجات المدعومة

منتجات مغلفة جاهزة، موزونة، سائبة، طازجة وقابلة للتلف، مبردة ومجمدة، منتجات تنظف أو تقطع أو تجهز أو تقسم، منتجات متعددة الوحدات، عبوات ومواد تغليف، عبوات مسترجعة بتأمين، منتجات مجانية/عينات، بضاعة أمانة (`Consignment`) عند الحاجة، وأرقام تسلسلية أو ضمان لبعض المنتجات.

## 7.3 نظام الباركود القياسي

- دعم قارئ الباركود السريع، وتعيين عدة باركودات للصنف نفسه.
- منع تكرار الباركود بين صنفين مختلفين، مع السماح بتوليد باركود داخلي قياسي (`EAN-13` يبدأ ببادئة داخلية مخصصة مثل `299` مع رقم تحقق `Check Digit` صحيح) للمنتجات التي لا تحمل باركود مصنع.
- دعم باركود موحد للصنف أو باركود مميز لكل عبوة/طبق/تشغيلة وفق سياسة الصنف.

# 8. شاشة الكاشير (POS Screen)

- تصميم فائق السرعة يعتمد على الإدخال الفوري بالباركود دون الحاجة للنقر بالماوس داخل حقل البحث في كل مرة (Auto-Focus / Global Barcode Listener).
- البحث الذكي بالاسم أو الكود أو الاختصار مع عرض الرصيد المتاح والسعر.
- عرض الاسم والسعر والكمية والوحدة والخصم والإجمالي بوضوح تام.
- تعديل الكمية والوحدة وفق الصلاحية، ودعم دمج السطور لنفس الصنف أو فصلها.
- البيع بالقطعة أو الوزن الكسري (مثل $0.350\text{ كجم}$) أو العبوة/الكرتونة.
- التبديل السلس بين سعر القطاعي والجملة والأسعار الخاصة حسب العميل أو الكمية.
- تطبيق العروض الترويجية تلقائيًا فور تحقق شروطها في السلة.
- خصم على صنف أو على إجمالي الفاتورة، مع طلب موافقة المشرف الفورية (PIN) عند تجاوز حدود الموظف أو النزول عن الحد الأدنى للسعر.
- **طرق الدفع:** نقدي، بطاقة بنكية (فيزا/ميزة)، محفظة إلكترونية (فودافون كاش/إنستاباي)، تحويل بنكي، وآجل (على حساب العميل).
- **الدفع المختلط (Split/Mixed Payment):** تقسيم سداد الفاتورة الواحدة على أكثر من وسيلة دفع (مثال: دفع $300$ جنيه نقدي + $250$ جنيه محفظة إلكترونية + $150$ جنيه آجل على حساب العميل).
- حساب الباقي للعميل في الدفع النقدي بوضوح مع أزرار فئات النقدية المصرية السريعة ($5, 10, 20, 50, 100, 200\text{ جنيه}$).
- تعليق فاتورة (أو عدة فواتير مع تسمية توضيحية) واستكمالها لاحقًا بضغطة زر.
- إلغاء صنف أو فاتورة وفق الصلاحيات مع تسجيل ذلك في سجل التدقيق.
- إعادة طباعة فاتورة سابقة مع وسمها بعبارة `"نسخة معاد طباعتها"`.
- اختيار العميل وعرض رصيده الحالي والحد الائتماني المتبقي قبل السماح بالبيع الآجل.
- عدم تسجيل البيع الآجل كنقدية محصلة في الخزينة.

# 9. الأسعار والعروض والخصومات

- اعتماد سعر قطاعي وسعر جملة وسعر خاص لعميل/مجموعة، وأسعار حسب الوحدة والعبوة والوزن.
- **أنواع العروض المدعومة:**
  1. اشترِ كمية $X$ واحصل على كمية $Y$ مجانًا أو بخصم $Z\%$ (من نفس الصنف أو صنف آخر - `BOGO`).
  2. خصم تدريجي عند بلوغ كمية معينة (مثال: قطعة بـ $20$ جنيه، و$3$ قطع بـ $50$ جنيه).
  3. حزمة مجمعة (`Bundle`) بسعر خاص.
  4. عروض مؤقتة بفترة زمنية (تاريخ/ساعة بداية ونهاية)، وعروض موسمية، وكوبونات خصم بشروط (حد أدنى للفاتورة، عدد مرات استخدام).
- يحسب النظام هامش الربح الفعلي بعد تطبيق العرض أو الخصم استنادًا إلى المتوسط المرجح للتكلفة (`WAC`).
- إذا أدى العرض أو الخصم إلى البيع بأقل من التكلفة، يعرض النظام تحذيرًا واضحًا ويتطلب موافقة إدارية محددة، مع السماح للمالك بتحديد استثناءات مسبقة (مثل تصفيات قرب انتهاء الصلاحية).

# 10. المشتريات والموردون

## 10.1 ملف المورد

الاسم التجاري وجهة الاتصال، الهاتف والعنوان والبريد، الرقم الضريبي والسجل التجاري عند الحاجة، رصيد افتتاحي (دائن/مدين)، شروط السداد وفترة الائتمان بالأيام، سجل فواتير المشتريات والمدفوعات والمرتجعات، الرصيد المستحق للمورد أو الرصيد الدائن لصالح المنشأة، كشف حساب تفصيلي، ملاحظات ومرفقات، عدة جهات اتصال/عناوين، مقارنة أسعار الموردين لنفس الصنف، وتقييم اختياري لأداء المورد.

## 10.2 فاتورة الشراء

- اختيار المورد والفرع والمخزن المستلم.
- إدخال الصنف بالباركود أو البحث، وإدخال كمية الشراء بوحدة الشراء الكبرى (مثلاً كرتونة) وتحويلها تلقائيًا لوحدة المخزون الصغرى (قطعة) لتحديث الرصيد.
- إدخال سعر الشراء، البونص المجاني من المورد (`Free Bonus Qty`)، الخصومات التجارية، والضرائب.
- **مصاريف الشحن والنقل على المشتريات (`Landed Cost`):** إتاحة خيار للمستخدم إما بتوزيع مصاريف النقل على تكلفة الأصناف المشتراة (حسب القيمة أو الوزن) أو تسجيلها كمصروف نقل مستقل.
- تاريخ الفاتورة، تاريخ الاستحقاق، ورقم فاتورة المورد الورقية، وإرفاق صورة الفاتورة.
- تسجيل رقم التشغيلة وتاريخ الصلاحية للأصناف الخاضعة للتتبع.
- تحديث المخزون وإعادة حساب المتوسط المرجح للتكلفة (`WAC`) وتحديث حساب المورد تلقائيًا فور اعتماد الفاتورة.

## 10.3 طرق السداد الثلاث -- معتمدة

1. **نقدي بالكامل:** دفع قيمة الفاتورة كاملة من الخزينة أو وسيلة الدفع المحددة فورًا.
2. **آجل بالكامل:** تسجيل كامل القيمة كمديونية مستحقة للمورد.
3. **جزئي:** دفع جزء من الخزينة وتسجيل المتبقي كمستحق في ذمة المنشأة للمورد.

يدعم النظام سداد أكثر من دفعة للفاتورة الواحدة لاحقًا، وجدولة تواريخ الاستحقاق، وإصدار إيصال دفع لكل دفعة، وكشف حساب مورد، وتقرير أعمار الديون ومستحقات الموردين.

**قاعدة مالية صارمة:** دفع فاتورة المورد الآجلة لاحقًا لا يسجل مصروف شراء جديدًا ولا يؤثر في قائمة الأرباح والخسائر؛ لأن قيمة البضاعة سُجلت في المخزون عند اعتماد الشراء. الدفع اللاحق يخفض رصيد الخزينة ويخفض المبلغ المستحق للمورد فقط.

## 10.4 مرتجعات المشتريات -- معتمدة

مثال: شراء $10$ كراتين وإرجاع كرتونتين تالفتين:
- اختيار فاتورة الشراء الأصلية (أو مرتجع حر للمورد بصلاحية المدير مع تحديد السعر).
- تحديد الصنف والكمية والتشغيلة والسبب: تالف، منتهي الصلاحية، خطأ توريد، أو غير ذلك.
- إرفاق مستند أو صورة اختيارية، واعتماد المرتجع حسب الصلاحية.
- خصم الكمية من المخزون، وحساب القيمة بسعر الشراء الأصلي في الفاتورة ومعالجة الخصم والضريبة وفق المستند الأصلي.
- تخفيض مستحقات المورد بقيمة المرتجع.
- **حالة الفاتورة المدفوعة بالكامل:** إذا كانت فاتورة الشراء الأصلية مسددة بالكامل، يتيح النظام خيارين: إما تسجيل المبلغ **كرصيد مدين مستحق للمنشأة لدى المورد** يُخصم تلقائيًا من الفواتير القادمة، أو تسجيل **استرداد نقدي فوري** يدخل الخزينة.

# 11. العملاء والبيع الآجل

- اعتماد ملف عميل وبيانات اتصال وعنوان ومنطقة، وسجل الفواتير والمشتريات، ورصيد افتتاحي، وحد ائتماني أقصى (`Credit Limit`)، وفترة سماح للسداد بالأيام.
- دعم البيع النقدي والآجل والجزئي، وتسجيل دفعات تحصيل كاملة أو جزئية مع طباعة إيصال استلام نقدية، وكشف حساب عميل حسب الفترة، ومرتجعات العملاء، وإظهار الرصيد قبل وبعد كل حركة على الفاتورة والإيصال.
- تنبيه بالعملاء المتأخرين عن السداد، وتقرير العملاء الأعلى مديونية.
- **القواعد المالية:**
  - البيع الآجل يزيد مديونية العميل ولا يزيد النقدية في الخزينة.
  - التحصيل يقلل مديونية العميل ويزيد رصيد الخزينة أو وسيلة الدفع المستلمة.
  - تجاوز الحد الائتماني يمنع إتمام الفاتورة الآجلة إلا بموافقة إدارية موثقة حسب سياسة المالك.
  - مرتجع العميل الآجل يخفض مديونيته، وإذا زاد عن مديونيته يتحول الفائض إلى رصيد دائن لصالح العميل أو يُرد نقدًا وفق سياسة الفرع.
  - تصحيح أي حركة معتمدة يكون بحركة عكسية موثقة، لا بحذفها.

# 12. المخزون وإدارة الحركات والتكلفة

## 12.1 سجل حركة الصنف ومعادلة الرصيد

يسجل النظام كل حركة في جدول دفتر المخزون (`Inventory Ledger`): الرصيد الافتتاحي، المشتريات، البونص، المبيعات، مرتجعات العملاء الصالحة لإعادة البيع، مرتجعات العملاء التالفة (تُوجه لمخزن التالف)، مرتجعات الموردين، التالف والهالك، المنتهي الصلاحية، منصرف الخام للتجهيز، وارد المنتج المجهز، فاقد التنظيف والتجهيز، الاستهلاك الداخلي، العينات والمجانيات، تحويلات الفروع الصادرة والواردة، وتسويات الجرد.

**معادلة الرصيد الإلزامية:**
$$\text{Current Stock} = \text{Opening Balance} + \sum \text{All Approved Inbound Movements} - \sum \text{All Approved Outbound Movements}$$
يُمنع حساب الرصيد باختصاره إلى (المشتريات ناقص المبيعات).

## 12.2 سياسة تقييم المخزون وتكلفة البضاعة المباعة (WAC Policy)

- يعتمد النظام رسميًا طريقة **المتوسط المرجح للتكلفة (Weighted Average Cost - WAC)** على مستوى كل فرع لحساب تكلفة البضاعة المباعة (`COGS`) وتقييم المخزون:
$$\text{New WAC} = \frac{(\text{Current Stock Qty} \times \text{Current WAC}) + (\text{New Purchase Net Cost})}{(\text{Current Stock Qty} + \text{New Purchase Qty} + \text{Bonus Qty})}$$
- **المخزون السالب ممنوع افتراضيًا.** أي استثناء للصنف/الفرع يحتاج اعتمادًا منفصلًا ومواصفة واضحة لتكلفة البيع المؤقتة وإعادة تقييمها وتسوية فرق التكلفة عند الشراء اللاحق، مع قيود مالية واختبارات تمنع تشويه الأرباح.

# 13. التشغيلات والصلاحية (Batch / Lot Tracking)

## 13.1 حفظ الدفعات وتعدد التواريخ

- مثال الشيبسي: دفعة أولى $50$ كيسًا بصلاحية ديسمبر $2025$، ودفعة ثانية $50$ كيسًا بصلاحية ديسمبر $2026$.
- يحفظ النظام رصيد كل دفعة (`Batch`) وتاريخ انتهائها منفصلًا في جدول التشغيلات حتى لو كان اسم الصنف والباركود التجاري واحدًا.
- لا يطلب النظام إدخال تاريخ كل كيس منفردًا عند الاستلام؛ يكفي إدخال تاريخ الصلاحية مرة واحدة لإجمالي الكمية المستلمة من نفس التشغيلة، مع السماح بتقسيم الكمية المستلمة إلى دفعتين أو أكثر إذا احتوت الكرتونة أو التوريدة على تواريخ صلاحية متعددة.

## 13.2 القاعدة الهندسية المعتمدة للخصم من الدفعات والربط مع الكاشير

1. **لا إجبار للزبون أو الكاشير:** لا يجبر النظام الزبون أو الكاشير على بيع قطعة بعينها إذا التقط الزبون كيسًا يحمل باركود المصنع الموحد.
2. **في حال مسح باركود داخلي مخصص للدفعة/الطبق:** يخصم النظام مباشرة من تلك الدفعة المحددة.
3. **في حال مسح باركود المصنع التجاري الموحد (`EAN-13`):** لأغراض تخصيص المخزون الدفتري فقط، وللحفاظ على تطابق أرصدة الدفعات مع الرصيد الإجمالي للصنف ($\sum \text{Batch Quantities} = \text{Total Product Stock}$)، يخصم النظام برمجيًا وتلقائيًا من أقدم دفعة غير منتهية في قاعدة البيانات (**Virtual FEFO Allocation**)، دون أن يدعي في التقارير أن الزبون التقط تلك الدفعة فعليًا، بل يسميها `"تخصيص تلقائي للأقدم - Virtual FEFO"`، مع توفير أداة سريعة لمسؤول المخزن (**"مطابقة تواريخ الرفوف"**) لتعديل توزيع الكميات بين الدفعات عند الجرد الفعلي دون المساس بالرصيد الإجمالي.
4. **تنبيهات الصلاحية:** اختيارية تشغيلًا وإيقافًا، ويحدد المالك مدة التنبيه المسبق ($30$ يومًا، $60$ يومًا، أو عدد أيام مخصص لكل قسم). تظهر التنبيهات في لوحة التحكم مع عرض الدفعات الأقدم أولًا لتسهيل ترتيب الرفوف (`Physical FEFO Merchandising`).
5. **سياسة المنتهي:** يُمنع بيع الأصناف المنتهية افتراضيًا مع تحذير واضح. لا يتيح البرنامج تجاوز المنع بقرار المدير إذا كان ذلك مخالفًا للقواعد القانونية السارية؛ تُراجع السياسة القانونية والتشغيلية قبل تفعيل أي استثناء مسموح.

# 14. تجهيز وتقسيم المنتجات (Stock Transformation / Preparation)

ميزة أساسية جوهرية في السوبرماركت المصري (الأجبان، اللانشون واللحوم الباردة، الزيتون والمخللات، الحلاوة والطحينة، المكسرات، الخضروات والفواكه، اللحوم والدواجن).

## 14.1 القواعد الحسابية المعتمدة للتجهيز والفاقد (مثال الجبنة الرومي والوزن المتغير)

**المدخلات الأساسية:**
- تكلفة شراء كتلة المادة الخام ($\text{Raw Batch Cost}$) $= 1,000\text{ جنيه}$.
- الوزن القائم قبل التنظيف ($\text{Gross Weight}$) $= 10\text{ كجم}$ ($10,000\text{ جرام}$).
- الوزن الصافي الصالح للبيع بعد التنظيف والتقشير ($\text{Net Yield Weight}$) $= 9.5\text{ كجم}$ ($9,500\text{ جرام}$).

**المعادلات الإلزامية في محرك النظام:**
1. **حساب الفاقد ونسبته:**
   $$\text{Waste Weight} = \text{Gross Weight} - \text{Net Yield Weight} = 10 - 9.5 = 0.5\text{ kg}$$
   $$\text{Waste Percentage} = \left(\frac{\text{Waste Weight}}{\text{Gross Weight}}\right) \times 100 = 5\%$$
2. **التكلفة الصافية للكيلوجرام الواحد بعد استيعاب الفاقد:**
   تُحمل تكلفة المادة الخام بالكامل ($1,000\text{ جنيه}$) على الوزن الصافي الصالح للبيع ($9.5\text{ كجم}$):
   $$\text{Net Cost per Kg} = \frac{1,000}{9.5} \approx 105.2632\text{ EGP/kg}$$
3. **وضع الإنتاج الأول -- أطباق متساوية الوزن/السعر (مثال الوثيقة المعتمد):**
   - عدد الأطباق الناتجة $= 10\text{ أطباق}$ متساوية (متوسط وزن الطبق $= 950\text{ جرامًا}$).
   - تكلفة الجبنة في الطبق الواحد $= \frac{1,000}{10} = 100\text{ جنيه}$.
   - سعر بيع الطبق المحدد $= 200\text{ جنيه}$.
   - مجمل ربح الطبق (قبل المصروفات التشغيلية) $= 200 - 100 = 100\text{ جنيه}$.
   - إجمالي قيمة البيع المتوقعة $= 2,000\text{ جنيه}$، وإجمالي مجمل الربح المتوقع $= 1,000\text{ جنيه}$.
4. **وضع الإنتاج الثاني -- أطباق بأوزان فعلية مختلفة (للتشغيل اليومي على الميزان):**
   - إذا قُسمت الـ $9.5\text{ كجم}$ إلى أطباق مختلفة الوزن (مثلاً طبق وزنه $0.250\text{ كجم}$ وطبق وزنه $0.400\text{ كجم}$ بحيث مجموع أوزان الأطباق $= 9.5\text{ كجم}$):
   - تكلفة المادة الخام للطبق $i$:
     $$\text{Tray Cost}_i = \text{Tray Weight}_i \times \text{Net Cost per Kg}$$
   - سعر بيع الطبق $i$:
     $$\text{Tray Price}_i = \text{Tray Weight}_i \times \text{Selling Price per Kg}$$

**قاعدة تكلفة معتمدة لا يجوز تغييرها:**  
تكاليف العبوات والعمالة **لا تُحمّل تلقائيًا على تكلفة الجبنة** في المثال المعتمد، وتعرض كمصاريف منفصلة عن تكلفة المادة الخام. إذا اشترت المنشأة عبوات بغرض التخزين فإن شراءها يُسجل أصل مخزون إلى أن تُستهلك؛ ثم تُعترف تكلفتها بالمصروف وفق السياسة المعتمدة، **دون الازدواج**. تحميل تكلفة العبوات أو العمالة على تكلفة المنتج خيار محاسبي مستقبلي يحتاج اعتمادًا واختبارات ترحيل مناسبة.

## 14.2 خطوات شاشة التجهيز والتقسيم

1. اختيار الصنف الخام والتشغيلة المصدر.
2. عرض الكمية المتاحة وتكلفتها الفعلية.
3. إدخال الوزن/الكمية المسحوبة قبل التنظيف أو التقطيع.
4. إدخال الوزن الصافي بعد المعالجة، وحساب الفاقد ونسبته تلقائيًا (مع تنبيه إذا تجاوز الفاقد النسبة المعيارية المحددة للصنف).
5. اختيار طريقة التقسيم: (عدد أطباق متساوية) أو (إدخال/قراءة أوزان الأطباق الفعلية من الميزان).
6. حساب تكلفة المادة الخام لكل طبق أو لكل كيلوجرام ناتج تلقائيًا.
7. إدخال سعر البيع وحساب هامش الربح المتوقع للطبق وللعملية بالكامل.
8. تحديد تاريخ التجهيز وتاريخ انتهاء الصلاحية الجديد للمنتج المجهز (يحسب تلقائيًا بناءً على مدة صلاحية الصنف بعد الفتح/التجهيز مع إمكانية تعديله).
9. اعتماد العملية: يخصم النظام الوزن القائم من مخزون المادة الخام، ويسجل الفاقد في سجل فاقد التجهيز، ويضيف الأطباق/الكمية الناتجة إلى مخزون الصنف المجهز بدفعة جديدة.
10. طباعة ملصقات الباركود تلقائيًا بعدد العبوات الناتجة.
11. **منع الازدواج:** بيع الطبق الجاهز على الكاشير يخصم من مخزون "الأطباق الجاهزة" ولا يخصم من مخزون "المادة الخام" مرة ثانية.

# 15. ملصقات الباركود للعبوات المجهزة والأرفف

- بعد اعتماد التجهيز، يطبع النظام تلقائيًا عدد الملصقات المطابق لعدد العبوات الناتجة، مع دعم معاينة الملصق وإعادة الطباعة حسب الصلاحية.
- **الحقول الأساسية على ملصق العبوة:** اسم السوبرماركت، اسم المنتج، سعر البيع، الباركود.
- **الحقول الاختيارية (تُفعل أو تُخفى بضغطة زر):** الوزن الصافي، سعر الكيلو، تاريخ التجهيز، تاريخ انتهاء الصلاحية.
- **أنواع الباركود المدعومة على الملصق (قابلة للضبط):**
  1. باركود موحد للصنف المجهز (للأطباق متساوية السعر والوزن).
  2. باركود ميزان قياسي (`EAN-13 Weight/Price Embedded`) يتضمن كود الصنف والوزن الفعلي أو السعر لكل طبق.
  3. باركود تشغيلة داخلي فريد (`Batch/Serial Barcode`) لتتبع كل طبق أو دفعة بدقة.
- دعم طباعة **ملصقات تسعير الأرفف (Shelf Price Tags)** عند تغيير أسعار الأصناف.
- يُمنع استخدام أي رقم باركود تجريبي ثابت في الكود؛ يجب توليد أرقام باركود فريدة بصياغة صحيحة والتحقق من عدم تصادمها في قاعدة البيانات.

# 16. المنتجات الموزونة والميزان الإلكتروني

- دعم البيع بالكيلوجرام والجرام والكميات الكسرية بدقة 3 خانات عشرية للوزن ($0.001\text{ كجم}$).
- **محرك فك ترميز باركود الميزان القياسي (Configurable Scale Barcode Parser):**
  - يدعم **صيَغًا شائعة قابلة للضبط** من `EAN-13` الخاص بالموازين والتي قد تستخدم بادئات داخلية من `20` إلى `29`، ولا يفترض أن كل هذه البادئات تعني وزنًا أو أن حقول كل موديل متطابقة:
    $$\underbrace{\text{PP}}_{\text{Prefix (2)}} \underbrace{\text{IIIII}}_{\text{PLU Code (5)}} \underbrace{\text{WWWWW}}_{\text{Weight in Grams or Price (5)}} \underbrace{\text{C}}_{\text{Check Digit (1)}}$$
  - مثال **تصحيحي حسابيًا لا يمثل صيغة كل الموازين**: الباركود `2100145007501` (رقم التحقق EAN-13 الصحيح `1`) يترجمه النظام عند إعداد حقول الوزن كما يلي: بادئة وزن `21`، الصنف ذو كود الميزان `00145`، والوزن `00750` جرامًا ($0.750\text{ كجم}$)، ويضربه في سعر الكيلو تلقائيًا على شاشة الكاشير.
  - إعدادات مرنة لمواضع الخانات ووحدات الوزن والموضع العشري وصيغة السعر/الوزن، مع **تجربة فعلية** لموديلات الميزان المستهدفة قبل ادعاء دعمها.
- دعم قراءة الوزن المباشر من الميزان المتصل بالكاشير عبر منفذ `RS-232 Serial / USB` مع دعم الوزن الصافي والوزن الفارغ (`Tare`).

# 17. التالف والهالك والاستهلاك الداخلي

- تسجيل كمية تالفة أو منتهية الصلاحية لكل صنف وتشغيلة.
- أسباب قابلة للتخصيص: انتهاء صلاحية، سوء تخزين، تلف نقل، تبريد غير مناسب، عبوة مكسورة، تلف تنظيف/تقطيع، مرتجع عميل غير صالح للبيع، استهلاك داخلي/ضيافة، عينة مجانية، أو سبب آخر.
- حفظ الكمية والوزن وتكلفة الوحدة (`WAC`) والقيمة الإجمالية للتالف والتاريخ والموظف، مع إرفاق صورة اختيارية واعتماد المدير حسب الصلاحية.
- خصم الكمية من المخزون المتاح وإدراج قيمتها في تقارير التالف وحسابات صافي الربح.

# 18. العبوات المسترجعة والتأمين (Returnable Containers & Deposits)

- دعم الزجاجات الغازية، جراكن المياه، الصناديق البلاستيكية، والعبوات القابلة للإرجاع (سواء مع العملاء أو مع الموردين).

- حفظ رصيد العبوات والتأمينات المحتجزة لدى العملاء أو المسددة للموردين، وتسوية المبلغ نقدًا أو خصمًا من الفاتورة عند إرجاع العبوة الفارغة، وتقرير بالعبوات غير المرتجعة.

# 19. الجرد المخزني (مع استمرار البيع دون توقف)

- جرد كامل أو جزئي حسب قسم أو رف أو مخزن فرعي أو تشغيلة.
- إدخال الجرد بالباركود أو اليدوي أو بالوزن، مع دعم الجرد من عدة هواتف Android متصلة بشبكة الفرع في وقت واحد.
- **المعادلة الهندسية للجرد أثناء استمرار البيع (Live Stocktake Delta Equation):**
  - عند فتح جلسة الجرد في اللحظة $T_0$، يأخذ النظام لقطة مرجعية للرصيد الدفتري لكل صنف ($\text{Snapshot Qty at } T_0$).
  - يستمر الكاشير في البيع أثناء الجرد، لكن **العد على الرف يحدث بعد $T_0$**؛ يجب توثيق وقت عدّ كل صنف، واحتساب الحركات المعتمدة بين لحظة المرجع ولحظة عدّ ذلك الصنف، أو تجميد حركة الصنف أثناء عده، حتى لا يُحسب بيع جارٍ كعجز وهمي.
  - عند اعتماد الجرد في اللحظة $T_1$، **يُمنع استبدال الرصيد الحالي بالكمية المجرودة مباشرة**؛ بعد تطبيع العد إلى لحظة المرجع $T_0$ (أو اعتماد مقارنة وقت العد) يحسب النظام فرق الجرد (العجز أو الزيادة):
    $$\Delta \text{Adjustment} = \text{Counted Qty Normalized to } T_0 - \text{Snapshot Qty at } T_0$$
  - ثم يُضاف $\Delta \text{Adjustment}$ كحركة تسوية جردية على الرصيد الحي الحالي في اللحظة $T_1$:
    $$\text{New Live Stock at } T_1 = \text{Current Live Stock at } T_1 + \Delta \text{Adjustment}$$
  - كما يتيح النظام خيار "تجميد حركة الصنف مؤقتًا أثناء جرده" أو "تحديد ما إذا كان الصنف المجرود قد بِيعت منه كمية قبل وصول الموظف للرف".
- اعتماد المدير للفروق الحساسة، وحفظ سجل كامل قبل وبعد الاعتماد مع تقييم الفروق بتكلفة `WAC` وبسعر البيع.

# 20. المصروفات والرواتب

- تصنيفات جاهزة قابلة للزيادة: إيجار، كهرباء، مياه، إنترنت، رواتب وأجور، نقل ومشال، صيانة، نظافة، أكياس ومواد تعبئة وتغليف، ضيافة، ومصروفات أخرى.
- تسجيل المبلغ والتاريخ والوقت والفرع والخزينة/طريقة الدفع والموظف، مع ملاحظات وإرفاق صورة إيصال، ودعم تذكير بالمصروفات الدورية المتكررة (مثل الإيجار الشهري).
- تسجيل الرواتب المصروفة كمصروفات وفق السياسة المحاسبية، أما **السلف التي تُسترد من الموظف فلا تُسجل مصروف رواتب فورًا** بل مستحقًا/ذمة على الموظف ثم تُسوّى عند الاستقطاع أو التسوية. تعديل المصروف المعتمد يكون بعكس أو تسوية موثقة لا بتغيير سجل أصلي بصمت.

# 21. الخزينة والورديات

- رصيد افتتاحي لكل خزينة، ودعم تعدد الخزائن (درج كاشير 1، درج كاشير 2، خزينة الإدارة الرئيسية للفرع).
- فصل أرصدة وسائل الدفع داخل كل وردية وخزينة: (نقدي بالدرج، بطاقات بنكية، محافظ إلكترونية، تحويلات بنكية).
- عمليات السحب والإيداع والتحويل بين الخزائن (مثل توريد عهدة الكاشير إلى خزينة المدير) بتوثيق الطرفين.
- فتح وردية بعهدة بداية الوردية (`Opening Float`)، وإغلاق الوردية باحتساب الرصيد المتوقع لكل وسيلة دفع ومقارنته بالرصيد الفعلي المعدود، وإظهار العجز (`Shortage`) أو الزيادة (`Overage`) وتسجيل السبب واعتماد المعالجة.

## 21.1 مصفوفة الربط المالي والمخزني التلقائي (Accounting Integrity Matrix)

| العملية | التأثير في المخزون | التأثير في الخزينة / وسائل الدفع | التأثير في حساب العميل / المورد | التأثير في قائمة الدخل (الربح) |
| :--- | :--- | :--- | :--- | :--- |
| **بيع نقدي / إلكتروني** | خصم الكمية المباعة | زيادة النقدية / وسيلة الدفع | لا يوجد | زيادة المبيعات + إثبات تكلفة البضاعة المباعة (`COGS`) |
| **بيع آجل** | خصم الكمية المباعة | **لا يتأثر (صفر)** | زيادة مديونية العميل | زيادة المبيعات + إثبات تكلفة البضاعة المباعة (`COGS`) |
| **تحصيل دفعة من عميل** | لا يتأثر | زيادة النقدية / وسيلة الدفع | تخفيض مديونية العميل | لا يتأثر (تحويل أصل مالي لآخر) |
| **شراء بضاعة (نقدي)** | زيادة المخزون وتحديث `WAC` | خصم من الخزينة | لا يوجد | لا يسجل كمصروف (أصل مخزني) |
| **شراء بضاعة (آجل)** | زيادة المخزون وتحديث `WAC` | **لا يتأثر (صفر)** | زيادة مستحقات المورد | لا يسجل كمصروف (أصل مخزني) |
| **سداد دفعة لمورد** | لا يتأثر | خصم من الخزينة | تخفيض مستحقات المورد | **لا يسجل كمصروف شراء جديد** |
| **تسجيل مصروف تشغيلي** | لا يتأثر | خصم من الخزينة | لا يوجد | يخصم من مجمل الربح للوصول لصافي الربح |
| **تسجيل تالف / هالك** | خصم الكمية من المخزون | لا يتأثر | لا يوجد | يثبت كخسارة تالف بالتكلفة (`WAC`) |

# 22. مرتجعات العملاء

- مرتجع كامل أو جزئي مربوط بالفاتورة الأصلية عبر مسح باركود الفاتورة أو رقمها (مع منع إرجاع كمية أكبر من الكمية المباعة في الفاتورة الأصلية بعد خصم أي مرتجعات سابقة عليها).
- السماح بـ "مرتجع بدون فاتورة أصلية" بصلاحية المدير فقط مع توثيق السبب.
- فحص حالة الصنف المرتجع عند الاستلام:
  1. **صالح لإعادة البيع:** يعود إلى المخزون المتاح للبيع.
  2. **تالف / مفتوح:** يُوجه تلقائيًا إلى سجل التالف ولا يضاف للمخزون الصالح.
- رد القيمة نقدًا أو إلى وسيلة الدفع الأصلية أو خصمها من مديونية العميل الآجل.

# 23. التقارير ولوحة التحكم ومبادئ عرض الربح

## 23.1 التقارير الشاملة

تغطي جميع تقارير المبيعات، الأرباح، تكلفة البضاعة المباعة، المشتريات، الموردين، العملاء، المصروفات، الخزينة والورديات، المخزون وتقييمه، كارت حركة الصنف، التشغيلات والصلاحية، التالف والفاقد، نتائج التجهيز والتقسيم، الجرد والفروقات، المرتجعات، العروض والخصومات، أداء الموظفين، ومقارنة الفروع، مع تصدير `Excel (.xlsx)` و`PDF` بتنسيق عربي `RTL` سليم.

## 23.2 المعادلات المالية الصارمة لعرض الربح

يجب أن يفصل النظام في شاشاته وتقاريره بصرامة بين التدفق النقدي (`Cash Flow`) وبين الربح المحاسبي (`Profitability`):
1. **صافي المبيعات:**
   $$\text{Net Sales} = \text{Gross Sales (Cash + Credit)} - \text{Sales Discounts} - \text{Customer Returns}$$
2. **تكلفة البضاعة المباعة (`COGS`):**
   $$\text{COGS} = \sum (\text{Net Sold Qty} \times \text{Item WAC at Time of Sale})$$
3. **مجمل الربح (`Gross Profit`):**
   $$\text{Gross Profit} = \text{Net Sales} - \text{COGS}$$
4. **صافي الربح التقديري (`Estimated Net Profit`):**
   $$\text{Net Profit} = \text{Gross Profit} - \text{Operating Expenses} - \text{Approved Spoilage/Waste Cost} \pm \text{Stocktake Variance Cost}$$

- **ممنوعات محاسبية:** لا تساوِ الربح برصيد الخزينة، لا تعتبر البيع الآجل نقدية محصلة، ولا تعتبر سداد المورد مصروفًا.

# 24. الضرائب والفواتير ومصمم القوالب

## 24.1 إعدادات الضرائب

- المالك يتحكم في إنشاء أنواع ضرائب متعددة (مثل ضريبة قيمة مضافة بنِسَب تُحدَّد وفق التشريع الساري، ضريبة الجدول، أو صفر/معفى)، وتحديد هل سعر البيع المدخل شامل الضريبة (`Tax-Inclusive`) أم غير شامل وتُضاف الضريبة عند البيع (`Tax-Exclusive`).
- حفظ نسخة ثابتة من نسبة وقيمة الضريبة داخل كل سطر فاتورة عند الإصدار حتى لا تتأثر الفواتير التاريخية بتعديل النسب لاحقًا.

## 24.2 مصمم الفواتير الداخلي (Dual-Mode Invoice Designer)

لتحقيق أعلى سرعة طباعة حرارية مع أقصى مرونة تصميم دون إبطاء الكاشير:
1. **مُنسق إيصالات الكاشير الحرارية (58 مم و80 مم - Block-Based Thermal Configurator):**
   - مصمم مرئي سريع يتيح للمالك (دون مبرمج): رفع الشعار وتحديد حجمه ومحاذاته، ترتيب أقسام الإيصال بالسحب والإفلات، إظهار أو إخفاء أي حقل (الرقم الضريبي، اسم الكاشير، رصيد العميل السابق والحالي، إجمالي التوفير في العروض، الباركود السفلي)، التحكم في حجم الخط وسماكته، وإضافة ترويسة ورسالة شكر وسياسة استرجاع.
   - يطبع بالأبيض والأسود فائق الوضوح لضمان السرعة الفورية على طابعات `ESC/POS`.
2. **مصمم الفواتير والسندات القياسية (مقاس A4 - Full PDF Visual Designer):**
   - يدعم الألوان الكاملة، الخلفيات، الجداول المخصصة، الشعارات الملونة، والتوقيعات لفواتير المبيعات والمشتريات وكشوف الحسابات.
- دعم حفظ قوالب متعددة (قالب للبيع، قالب للمرتجع، قالب لإيصال التحصيل) وتخصيص قالب لكل فرع أو طابعة، مع ضمان أن إعادة طباعة فاتورة قديمة تعرض بياناتها التاريخية الأصلية دون تحريف.

# 25. الطباعة والأجهزة (Hardware Abstraction Layer)

- دعم طابعات الإيصالات الحرارية $58\text{ مم}$ و$80\text{ مم}$، وطابعات الليزر/الحبر `A4`، وطابعات ملصقات الباركود (`ZPL / TSPL / ESC-POS Label`).
- **قاعدة عدم فقد الفاتورة:** اعتماد الفاتورة وحفظها في قاعدة البيانات يتم أولًا في معاملة ذرية مستقلة عن الطابعة؛ إذا انقطع اتصال الطابعة أو نفد الورق، تُحفظ الفاتورة سليمة $100\%$ وتوضع مهمة الطباعة في طابور إعادة الطباعة (`Print Spooler Queue`) مع تنبيه الكاشير.

# 26. النسخ الاحتياطي والاستعادة (Safe Hot Backup & Encryption)

## 26.1 السياسة المعتمدة والآلية الهندسية

- نسخة احتياطية تلقائية يوميًا (أو عند إغلاق الوردية) تُحفظ محليًا على هارد جهاز Windows الرئيسي، وتُرفع تلقائيًا إلى `Google Drive` عند توفر الإنترنت بعد ربط حساب المالك عبر `OAuth 2.0`.
- **آلية النسخ الذري الآمن أثناء التشغيل (`SQLite Hot Backup`):**
  - يُمنع نسخ ملف قاعدة البيانات مباشرة أثناء عمل الخادم بطريقة غير متسقة؛ استخدم آلية نسخ حي معتمدة مثل SQLite Backup API أو أمر SQLite الرسمي:
    `VACUUM INTO 'backup_temp_path.db';`
  - يتم ضغط الملف الناتج، وحساب بصمة التحقق `SHA-256 Checksum`، ثم تشفيره بخوارزمية `AES-256-GCM` قبل حفظه أو رفعه للسحابة.

## 26.2 قاعدة الحماية الصارمة (Zero-Loss Retention Policy)

- **لا يتم حذف النسخ الأقدم وفق سياسة الاحتفاظ (30 نسخة يومية افتراضيًا) إلا بعد وجود نسخة بديلة سليمة ومختبَرَة، والتحقق من سلامة النسخ المحلية، ومن نجاح رفع النسخة التي يُشترط رفعها للسحابة؛ ويُحمى حد أدنى من النسخ المحلية حتى عند فشل الرفع.**
- إذا فشل الرفع إلى `Google Drive` بسبب انقطاع الإنترنت، تبقى النسخة المحلية محفوظة وتُجدول في طابور الرفع التلقائي فور عودة الاتصال.
- قبل استعادة أي نسخة احتياطية، يقوم النظام تلقائيًا بأخذ **"نسخة أمان طارئة (Pre-Restore Safety Snapshot)"** من البيانات الحالية، ولا يستبدل البيانات إلا بموافقة صريحة من المالك وبعد فك تشفير النسخة والتحقق من سلامة هيكل جداولها.

# 27. الترخيص والاشتراك والأمان ضد التلاعب

## 27.1 السعر والسياسة المعتمدة

- اشتراك سنوي فقط (دون اشتراك شهري): **500 جنيه مصري لكل جهاز سنويًا**.
- كل جهاز Windows أو Android يحتاج ترخيصًا مستقلًا مرتبطًا بالمنشأة والفرع ومعرف تثبيت آمن قابل للإدارة؛ تُصمم سياسة بصمة الجهاز وإجراءات الاستبدال وإعادة التفعيل وفق قيود الخصوصية واختبارات الاعتمادية على Windows وAndroid، دون الاعتماد المطلق على معرف عتادي واحد.
- تنبيه تلقائي قبل انتهاء الاشتراك بـ $30$ و$15$ و$7$ أيام.

## 27.2 التوقيع الرقمي ومنع التلاعب بالتاريخ (Offline Cryptographic Licensing)

- يعمل التفعيل والتجديد دون الحاجة لاتصال بالإنترنت عبر **كود تفعيل موقع رقميًا بتشفير غير متماثل (`Ed25519 Digital Signature`)**:
  - يحتوي تطبيق العميل على المفتاح العام (`Public Key`) فقط للتحقق من صحة الكود.
  - توجد أداة إصدار مفاتيح التفعيل (`tools/license_keygen/`) **خارج تطبيق العميل**؛ يبقى المفتاح الخاص في بيئة إصدار محمية/أداة خاصة لدى مالك المنتج ولا يُنشر في المستودع أو حزم التثبيت، ويُوقّع ترخيص الجهاز بعد التحقق من عملية الدفع والإجراءات المعتمدة.
- **حماية صارمة ضد إرجاع تاريخ الجهاز (Anti-Clock Rollback Protection):**
  - يحتفظ النظام بختم زمني متزايد مشفر (`Monotonic High-Water Mark Timestamp`) يتحدث مع كل عملية بيع أو حركة أو نبضة تشغيل.
  - إذا عاد وقت الجهاز عن آخر ختم موثوق بما يتجاوز عتبة سياسة قابلة للضبط (مبدئيًا 15 دقيقة)، يظهر وضع أمان مقيّد مع سجل تدقيق ومسار استعادة مرخّص؛ **لا يُفترض أن ساعة الجهاز موثوقة أو أن ختمها المحلي وحده يمنع التلاعب**. اختبر تغيّر التوقيت والتوقيت الصيفي وفقد بطارية الساعة وترحيل الجهاز.

## 27.3 وضع القراءة فقط بعد انتهاء الاشتراك (Strict Read-Only Enforcement)

- عند انتهاء صلاحية الترخيص، يتحول الجهاز المنتهي ترخيصه فورًا إلى **وضع القراءة فقط (Read-Only Mode)**:
  - يُسمح باستعراض كافة البيانات القديمة والفواتير والتقارير والمخزون وكشوف الحسابات وتصدير البيانات وأخذ النسخ الاحتياطية.
  - يُمنع إضافة أو تعديل أو حذف أي سجل، أو تسجيل مبيعات أو مشتريات أو مصروفات أو تحصيلات أو مدفوعات أو حركات مخزون جديدة.
  - **يُفرض وضع القراءة فقط في طبقة الخدمات والخادم المحلي (`Domain & API Middleware Guard`) وليس بمجرد إخفاء الأزرار في الشاشة.**
  - انتهاء ترخيص جهاز فرعي لا يعطل الأجهزة الأخرى التي تمتلك تراخيص سارية.

# 28. الاستيراد والتصدير والمساعدة وحالة النظام

# 29. المعمارية التقنية وعقد البيانات الصارم

## 29.1 حزمة التقنيات المعتمدة (Tech Stack)

- **إطار العمل:** `Flutter` & `Dart` (تطبيق موحد لـ Windows وAndroid).
- **إدارة الحالة والتنقل:** `Riverpod` (مع Code Generation) و`GoRouter`.
- **قاعدة البيانات المحلية:** `SQLite 3` (في وضع `WAL`) مدارة عبر مكتبة `Drift` مع ترحيلات إصدارية مختبرة (`Schema Migrations`).
- **خادم الفرع المحلي:** `Dart Shelf` + `shelf_router` + `shelf_web_socket` يعمل كخدمة خلفية داخل تطبيق Windows الرئيسي.
- **تمثيل الأموال والأوزان (قواعد صارمة لا تقبل التهاون):**
  - **الأموال والأسعار والتكاليف:** تُستخدم أعداد صحيحة للقروش (`1 EGP = 100 قرش`) عند التسوية النقدية؛ أما حساب التكلفة والمتوسط المرجح وأسعار الوحدة فقد يحتاج **نوع Decimal أو أعداد صحيحة بوحدة فرعية أدق ومحددة على مستوى المجال**، مع سياسة تقريب واضحة ومتسقة. يُمنع `float/double` لحساب المال.
  - **الأوزان والكميات:** تُخزن بأصغر وحدة أساس محددة لكل صنف (جرام/مل/قطعة، أو وحدة أدق عند الحاجة)، أو Decimal ثابت الدقة؛ تُجرّب التحويلات المتسلسلة مع منع كسر الوحدات غير القابلة للتجزئة.
- **الأمان:** تجزئة كلمات المرور والـ PIN عبر `Argon2id` أو `PBKDF2-HMAC-SHA256`، وتشفير النسخ الاحتياطية بـ `AES-256-GCM`، وتوقيع التراخيص بـ `Ed25519`.

## 29.2 عقد جداول قاعدة البيانات المنطقي (Core Logical Schema Contract)

**اعتماد التصميم المنطقي لجميع الوحدات يكون مبكرًا، أما الإنشاء الفعلي للجداول فيتم بترحيلات متدرجة مع كل ميزة مكتملة**. لا تُفرض أعمدة `branch_id`, `is_deleted`, `sync_status` على كل جدول بلا تمييز؛ بعضها يجب ألا يحوي حذفًا منطقيًا أصلًا (كالدفاتر المعتمدة)، وبعضها نطاقه منشأة لا فرع. الجداول التالية خريطة مستهدفة قابلة للتحسين بعد تصميم العلاقات والقيود:
1. **الهوية والفرع والترخيص:** `tenants`, `branches`, `warehouses`, `devices`, `licenses`, `monotonic_clock_guard`, `users`, `roles`, `permissions`, `audit_logs`.
2. **الكتالوج والتسعير والعروض:** `categories`, `brands`, `units`, `products` (شاملة `scale_plu`, `wac_cost`, `tax_code_type`, `tax_item_code`, `tracking_type`), `product_units_barcodes`, `branch_product_overrides`, `price_history`, `promotions`, `coupons`.
3. **المخزون والتشغيلات والتجهيز:** `product_batches` (شاملة `batch_number`, `expiry_date`, `quantity_on_hand`), `inventory_ledger` (سجل حركات شامل غير قابل للحذف), `stock_preparations` (رأس وتفاصيل عمليات تجهيز الجبنة واللحوم والفاقد), `stocktake_sessions`, `stocktake_items` (شاملة `snapshot_qty`, `counted_qty`, `delta_qty`), `stock_transfers`, `returnable_containers_ledger`.
4. **المشتريات والموردون:** `suppliers`, `purchase_invoices`, `purchase_invoice_items`, `purchase_returns`, `supplier_payments`, `supplier_ledger`.
5. **المبيعات والعملاء والخزينة:** `customers`, `sales_invoices` (شاملة `immutable_snapshot_json`), `sales_invoice_items`, `sales_payments` (لدعم الدفع المختلط), `sales_returns`, `customer_collections`, `customer_ledger`, `safes`, `shifts`, `safe_transactions`, `expenses`, `expense_categories`.
6. **المزامنة والطباعة والنسخ الاحتياطي:** `sync_outbox_queue`, `sync_inbox_log`, `invoice_templates`, `print_jobs_queue`, `backup_logs`.

# 31. خطة التنفيذ المرحلية المعدّلة (مانعة لإعادة الهيكلة)

- **المرحلة 1 -- الأساس المعماري وعقد البيانات الشامل والخادم المحلي:**
  إنشاء المستودع، **خريطة كيانات وعلاقات لجميع الوحدات** مع تنفيذ الجداول الجوهرية والترحيلات الأولى فقط؛ تأسيس خدمة الخادم المحلي (`Dart Shelf` أو بديل معتمد) ومسار العمليات الموثق (`Repository/Service`)، نظام الهوية والصلاحيات والتدقيق وقاعدة ترخيص أولية قابلة للاختبار، ملف المنشأة والفروع، والواجهة العربية/الإنجليزية بالوضعين الفاتح والداكن.
- **المرحلة 2 -- الكتالوج والمخزون والتشغيلات والمشتريات:**
  الأصناف والوحدات المتعددة والباركود، الموردون، فواتير المشتريات وحالات السداد الثلاث، حساب المتوسط المرجح للتكلفة (`WAC`)، مرتجعات المشتريات، التشغيلات والصلاحية ومنطق `Virtual FEFO`، التنبيهات، سجل حركة المخزون، الجرد الحي بمعادلة الفروق ($\Delta$)، والتالف والعبوات المسترجعة.
- **المرحلة 3 -- نقطة البيع (POS) والعملاء والعروض:**
  شاشة الكاشير فائقة السرعة، طرق الدفع والدفع المختلط، تعليق الفواتير، العملاء والبيع الآجل والحد الائتماني والتحصيلات، محرك العروض والخصومات والتحذير عند البيع بأقل من التكلفة، ومرتجعات المبيعات.
- **المرحلة 4 -- التجهيز والتقسيم والميزان وملصقات الباركود:**
  شاشة تحويل الخام إلى منتج مجهز (مثال الجبنة الرومي والأوزان المتساوية والمتغيرة)، حساب الفاقد والتكلفة الصافية، طباعة ملصقات الباركود، ومحرك فك باركود الميزان القياسي (`Prefix 20-29`).
- **المرحلة 5 -- المصروفات والخزينة والورديات والتقارير:**
  المصروفات والرواتب، الخزائن المتعددة، فتح وإغلاق الورديات (العادي والأعمى) ومعالجة العجز والزيادة، لوحات التحكم حسب الدور، والتقارير التفصيلية وتصدير `Excel` و`PDF`.
- **المرحلة 6 -- ربط أجهزة الشبكة المحلية ومزامنة الفروع:**
  **توسيع** اتصالات الخادم الذي تأسس في المرحلة 1 عبر اكتشاف `mDNS` وربط `QR Code` لأجهزة Android وWindows الإضافية، وتحويلات المخزون بين الفروع (إرسال واستلام مؤكد)، والمزامنة السحابية مع الإدارة الرئيسية ومعالجة انقطاع الاتصال.
- **المرحلة 7 -- النسخ الاحتياطي المشفر ومصمم الفواتير والضرائب:**
  النسخ الذري المحلي (`VACUUM INTO`) والرفع التلقائي إلى `Google Drive` مع سياسة الاحتفاظ الآمنة، الاستعادة المحمية، مصمم الفواتير الحرارية (`58mm/80mm`) و`A4`، وإعدادات الضرائب.
- **المرحلة 8 -- اختبارات القبول الشاملة وحزم الإصدار:**
  تنفيذ اختبارات القبول الـ 34 آليًا ويدويًا، اختبارات الأداء مع قواعد بيانات ضخمة ($50,000+$ صنف و$500,000+$ حركة)، دليل المستخدم، وحزم التثبيت النهائية لـ Windows (`MSIX/InnoSetup`) وAndroid (`APK`).

# 32. اختبارات القبول الإلزامية (34 اختبارًا حاسمًا)

لا يعتبر المنتج جاهزًا للتسليم قبل اجتياز كافة الاختبارات التالية فعليًا:
1. إنشاء منشأتين مستقلتين والتأكد من عدم اختلاط البيانات.
2. إنشاء عدة فروع بصلاحيات منفصلة ومخازن فرعية.
3. تشغيل فرع دون إنترنت واستمرار العمل محليًا بالكامل.
4. فصل الاتصال أثناء البيع ثم إعادته دون تكرار الفاتورة (`Idempotency`).
5. مزامنة العملية مرة واحدة فقط حتى مع إعادة الإرسال المتكرر.
6. تحويل بضاعة بين فرعين مع إرسال واستلام مؤكدين وعدم إتاحة الكمية قبل تأكيد الاستلام.
7. شراء نقدي وآجل وجزئي والتحقق من دقة أرصدة المخزون والخزينة والمورد و`WAC`.
8. مرتجع مورد بعد دفع الفاتورة بالكامل وتسجيله كرصيد لصالح المنشأة أو استرداد نقدي.
9. بيع نقدي وآجل ومختلط والتحقق من الخزينة ومديونية العميل.
10. تحصيل جزء من دين عميل ودفع جزء من مستحق مورد والتحقق من عدم تسجيل سداد المورد كمصروف.
11. تطبيق خصم وعرض والتحقق من هامش الربح وظهور التحذير وطلب موافقة المشرف عند البيع بأقل من التكلفة.
12. تشغيلات متعددة للصنف نفسه بتواريخ مختلفة والتحقق من الخصم التلقائي (`Virtual FEFO`) عند مسح الباركود الموحد.
13. تنبيه الصلاحية حسب المدة الاختيارية وترتيب الدفعات الأقدم.
14. عدم ادعاء معرفة الدفعة المباعة فعليًا في حال البيع بباركود المصنع الموحد، وتوفر أداة مطابقة الرف.
15. تجهيز $10\text{ كجم}$ جبنة بتكلفة $1,000\text{ جنيه}$ إلى $9.5\text{ كجم}$ صافي و$0.5\text{ كجم}$ فاقد ($5\%$)، وتجربة تقسيمها إلى $10$ أطباق متساوية ($100\text{ جنيه}$ تكلفة الطبق و$200\text{ جنيه}$ سعر بيع و$100\text{ جنيه}$ مجمل ربح)، وتجربة تقسيمها لأوزان متغيرة بحساب تكلفة الكيلو الصافي ($105.26\text{ جنيه}$).
16. عدم خصم المادة الخام مرة ثانية عند بيع الطبق الجاهز على الكاشير.
17. طباعة ملصق باركود باسم السوبرماركت واسم المنتج والسعر والباركود، مع إظهار/إخفاء الوزن والصلاحية.
18. اختبار باركود المنتجات متعددة الوحدات وباركود الميزان القياسي (`Prefix 20-29`).
19. اختبار الجرد الحي أثناء استمرار البيع والتحقق من معادلة الفروق ($\Delta \text{Adjustment}$) دون مسح مبيعات الكاشير التي تمت أثناء الجرد.
20. اختبار العجز والزيادة عند إغلاق الوردية (في الوضع العادي والوضع الأعمى).
21. إعادة طباعة فاتورة قديمة بعد تغيير اسم المنشأة أو سعر الصنف أو نسبة الضريبة والتأكد من بقاء بيانات الفاتورة التاريخية ثابتة دون تغيير.
22. اختبار قوالب الطباعة $58\text{ مم}$ و$80\text{ مم}$ و`A4` ودعم العربية `RTL` واتجاه الأرقام السليم.
23. التحقق من صلاحيات الكاشير وعدم كشف التكلفة والأرباح افتراضيًا على مستوى الشاشة والـ API.
24. تسجيل المصروفات والرواتب والتحقق من تأثيرها في صافي الربح وعدم تكرار احتسابها.
25. إنشاء نسخة احتياطية ذرية أثناء عمل النظام (`VACUUM INTO`) وتشفيرها ورفعها إلى `Google Drive`.
26. فصل الإنترنت أثناء النسخ الاحتياطي ثم التحقق من رفع النسخة تلقائيًا عند عودة الاتصال.
27. التحقق من عدم حذف النسخ القديمة قبل التأكد من نجاح النسخة الجديدة وسلامة بصمتها `SHA-256`.
28. استعادة نسخة احتياطية في بيئة اختبار والتحقق من أخذ نسخة أمان تلقائية قبل الاستعادة.
29. انتهاء الترخيص السنوي والتحول الفوري إلى وضع القراءة فقط على مستوى الواجهة والـ API دون حذف أي بيانات.
30. اختبار كود تفعيل صالح وغير صالح ومكرر ومخصص لجهاز آخر، واختبار **إرجاع ساعة الجهاز للوراء** والتأكد من قفل النظام ضد التلاعب بالوقت.
31. التحقق من أن انتهاء ترخيص جهاز فرعي لا يعطل الأجهزة الأخرى ذات التراخيص السارية.
32. اختبار الأداء مع قاعدة بيانات تحتوي على $50,000$ صنف و$500,000$ حركة مع التحقق من معيار أداء مقاس ومُعلن (`p95`) على الأجهزة المستهدفة؛ **50ms هدف طموح للبحث المحلي بعد تهيئة البيانات وليس ضمانًا لكل قراءة/بيع/طباعة**.
33. اختبار ترحيل قاعدة البيانات (`Schema Migration`) بين إصدارين دون فقد أي بيانات.
34. اختبار سجل التدقيق الأمني والتأكد من تسجيل القيم قبل وبعد التعديل ومنع الحذف النهائي للحركات.

# 34. قواعد مالية وتقنية إضافية تمنع الأخطاء

## 34.1 دفتر القيود الداخلي

- يمثل محرك الدفتر المزدوج (`journal_entries` + `journal_lines`) كل حركة مالية معتمدة بقيود متوازنة: مجموع المدين يساوي مجموع الدائن بالعملة/الوحدة النقدية نفسها. يربط القيد بعملية المنشأ ومعرف عدم التكرار.
- يستخرج النظام أرصدة العملاء والموردين والنقدية والمخزون من دفاتر الحركات والقيد الداخلي؛ أي جداول أرصدة مجمعة تستخدم كـ projection/cache قابلة لإعادة البناء، ولا تكون المرجع الوحيد غير القابل للمطابقة.
- مثال مبسط لبيع نقدي 100 جنيه وتكلفة 70 جنيه قبل الضرائب: مدين خزينة 100 / دائن مبيعات 100، ثم مدين تكلفة مبيعات 70 / دائن مخزون 70. ما عدا الضرائب/الخصومات التي تُعالج حسب فاتورة الواقعة.
- مثال شراء آجل بقيمة 300 جنيه: مدين مخزون 300 / دائن مورد 300؛ السداد لاحقًا مدين مورد / دائن خزينة. لا ينشأ مصروف جديد عند السداد.
- صرف/مرتجع/إلغاء حركة معتمدة = مستند عكسي ومبرر؛ لا حذف صامت أو تعديل تاريخي لدفاتر أصلية.
- كل عملية مالية تؤثر على أكثر من سجل (مبيعات، مخزون، دفاتر، خزينة، outbox) تتم داخل transaction محلي واحدة؛ إذا فشل جزء تتراجع العملية كلها. تُحفظ مهمة الطباعة بعد النجاح ويمكن إعادة إرسالها.

## 34.2 تزامن الكاشير والاتصال

- خادم الفرع **هو المرجع الوحيد** لاعتماد المبيعات على أجهزة LAN؛ يستخدم قفلًا/تسلسلًا مناسبًا للتخفيض من الرصيد والتحقق من الائتمان منعًا للتنافس.
- مفاتيح عدم التكرار لها نطاق `(tenant_id, branch_id, device_id, operation_type, idempotency_key)`، ويحتفظ الخادم بنتيجة الطلب للرجوع إليها إذا تكرر؛ لا يكرر خصم المخزون أو استلام الدفع.
- تنشأ أحداث outbox بالمعاملة ذاتها وتُرسل لاحقًا؛ المعالجة المركزية deduplicated، مع تقارير توازن واتساق دورية.
- لا يعتمد رقم الفاتورة على ساعة الجهاز وحدها؛ لكل فرع/جهاز تسلسل فريد مقيد داخل الخادم، مع snapshot ثابت للترقيم والتاريخ.
- **انقطاع الإنترنت الخارجي ≠ انقطاع LAN ≠ توقف Windows host**؛ لكل حالة واجهة واضحة وخطة استعادة وأثر معلن على البيع.

## 34.3 الدقة والحماية

- حساب الأموال `Decimal`/وحدات صحيحة مع سياسة rounding موحدة (على السطر، إجمالي الفاتورة، الضريبة، التخصيص بين وسائل الدفع)، واختبارات عدم ضياع قرش في عملية الدفع المختلط.
- تحويل الوحدات النسبية/الهرمية باستخدام Rational/Decimal ثابت الدقة؛ لا خصم صنف مرتين عند استخدام عدة باركودات.
- منع التلاعب من واجهة الكاشير وحدها غير كافٍ؛ فحص RBAC وفترة الترخيص على كل أمر كتابة في service/API مع logging.
- النسخ المشفرة تحتاج إدارة مفتاح استرداد منفصلة ومحفوظة بأمان؛ نجاح SHA-256 وحده لا يثبت أن نسخة النظام قابلة للاستعادة: نفذ restore drills منتظمة.
- بيانات شخصية وأرقام هواتف العملاء تُحمى بصلاحيات ونسخ مشفرة وسجلات عرض/تصدير مناسبة؛ تعقيم سجلات الأخطاء من الأسرار.

# 35. معايير اكتمال المرحلة (Definition of Done)

لا تعتبر أي وحدة منجزة قبل توفر: (1) نموذج البيانات والقيود/الترحيلات، (2) منطق domain فعلي، (3) API/Repository وربط الواجهة، (4) صلاحيات وAudit، (5) سيناريوهات الفشل والاتصال، (6) اختبارات unit/integration ونتائجها، (7) تجربة RTL/Windows/Android الملائمة، (8) توثيق تشغيل مختصر، (9) تقرير ما نُفذ وما لم يُنفذ، (10) موافقة المالك عند الانتقال لمرحلة كبيرة جديدة.

```gherkin
  Given a cashier device lost connection to the Windows branch host
  When a checkout is attempted
  Then no final success invoice is displayed until the host confirms commit
  And a retry uses a stable idempotency key
```

# 37. التحقق قبل إطلاق البرنامج التجاري

- فحص التوافق الضريبي المصري **من المصادر الرسمية الحالية** ونطاق نشاط المنشأة والضرائب والأكواد المطلوبة؛ لا تُفسر أي أمثلة ثابتة كنسبة قانونية عامة.
- اختبار فعلي للطابعات والماسحات والموازين المطلوبة، ومدى دعم Android/Windows للاتصال، وقياس الأداء المعلن على أجهزة حقيقية بأحجام بيانات واقعية.
- اختبارات قبول للانقطاع أثناء دفع مختلط، سقوط الطاقة أثناء حفظ العملية، قفل SQLite، فساد نسخة احتياطية، تعارض تحويل فرعي، إعادة تشغيل الخادم، ترقية schema، وأمان نقل الترخيص.
- اختبار تعدد منشآت مع tenant separation، وتفويض المدير/الكاشير وتصدير البيانات، وخطة حذف/نقل بيانات العميل قانونيًا عند انتهاء استخدام الخدمة.
- نشر سجل تغييرات، ونسخة مثبتة من الاعتماديات مع مراجعة تراخيصها التجارية والتنبيهات الأمنية، ومفتاح توقيع خاص لا يوجد بالمستودع.
- **لا يوجد ضمان "100% بلا فقد" في كل انقطاع كهربائي أو عطل عتادي**؛ توضع أهداف RPO/RTO، وUPS إن لزم، ونسخ خارج الجهاز، واختبارات استعادة موثقة.

# 38. تعليمات للمطور/Antigravity/أي فريق تنفيذ

1. اقرأ المستند كاملاً وقدم مصفوفة `BR/ENG/DEC/LEGAL/AT` تشمل الوحدات والاعتماديات، وحدد النقاط الناقصة دون اختراع قرار نهائي.
2. أنشئ `docs/architecture/` بمخطط النظام، `docs/adr/` لقراراته، `docs/acceptance/` للاختبارات، و`docs/open-decisions.md` لسجل الموافقات.
3. أسس المشروع والمستودع وCI، وخادم الفرع المحلي ومبدأ المخطط المنطقي قبل توسيع صفحات الواجهة.
4. نفذ وحدات صغيرة رأسياً من الواجهة حتى قاعدة البيانات مع transaction وaudit واختبار، لا شاشات تجريبية تدّعي اكتمال الوظيفة.
5. لا تمسح بيانات تاريخية معتمدة؛ استخدم قيودًا عكسية ومراجعة مؤيدة بالمصدر.
6. عند كل مرحلة أرفق قائمة الملفات المعدلة، أوامر الاختبارات ونتائجها، ما تعذّر اختباره دون جهاز فعلي/حساب خارجي، والمخاطر المتبقية.
7. لا تضف ميزة جديدة خارج هذه الوثيقة أو تغير شرطًا معتمدًا دون موافقة مالك المشروع.
8. **تعتبر هذه الوثيقة نقطة انطلاق فنية مُحسّنة وليست دليلًا على تنفيذ التطبيق أو اجتياز اختبارات الإنتاج.**
