# جاهزية الإطلاق التجاري — حالة موثّقة ومهام تشغيل Posegypt

هذه الوثيقة تسجّل ما نُفّذ واختُبر، ولا تمنح اعتمادًا ضريبيًا أو أمنيًا أو محاسبيًا.
**الحالة: نسخة تطوير قابلة للبناء — ليست إصدارًا تجاريًا معتمدًا بنسبة 100%.**

## ما نُفّذ فعليًا

- تطبيق Flutter للعربية وWindows وAndroid، مع عمليات بيع وشراء أساسية ووردية وتقارير.
- خدمة Dart/Shelf/SQLite بعمليات ذرية ومعاملات Idempotency-Key ودفتر مزدوج القيد.
- بيع بكمية أساس كسرية أو بوحدة بديلة (كرتونة/علبة) لها معامل تحويل وسعر مستقل.
- قاعدة البيانات v2 مع ترحيل تدريجي من v1، ورفض فتح قاعدة بيانات أحدث من نسخة البرنامج.
- اختبار عودة المخزون والديون بعد إعادة تشغيل SQLite، وحماية المرتجعات الجزئية من فقد القروش.
- نسخة احتياطية مشفرة AES-256-GCM، مع اختبار فك التشفير والتدقيق، ومنع تزامن تشغيل نسختين، وسياسة احتفاظ محافظة.

## تشغيل نسخة احتياطية موثّقة

**المتطلبات:** Python 3.12، وملف SQLite تابع فعلاً لخادم Kasher، وكلمة مرور طويلة
تُحقن عند التشغيل من خزنة أسرار موثوقة، ومجلد احتياطي منفصل خاص وغير مكشوف للعموم.

من جذر المستودع:

```powershell
python -m pip install -r tools/requirements-backup.txt
# اضبط KASHER_BACKUP_PASSWORD داخل جلسة التشغيل من مصدر أسرار آمن.
python tools/scheduled_backup.py server/data/kasher.sqlite3 D:/KasherPrivateBackups --keep 14
```

عند النجاح تُرجع الأداة JSON فيه `status: verified` واسم ملف النسخة.
تُجرى الخطوات التالية بالترتيب: تدقيق المصدر → لقطة SQLite متسقة مع WAL →
تشفير AES-GCM → استعادة مؤقتة للتحقق → تدقيق المستعاد → تقليص عدد النسخ
السابقة إن تجاوز الحد. إذا فشلت الاستعادة **لا تُحذف نسخة قديمة**.
يُمنع تشغيل مهمتين متوازيتين بقفل `.kasher-backup.lock`؛ في حال بقاء
القفل بعد انقطاع كهرباء يجب أن يتحقق المشغّل من توقف المهمة قبل حذفه.

**قيود فعلية:** هذا أمر تشغيل واحد، وليس مجدولًا داخل Windows تلقائيًا.
تتطلب الجدولة ربط Windows Task Scheduler وخزنة أسرار مناسبة تحت حساب الخدمة،
ومراقبة فشل المهمة وإجراء اختبار استعادة ميداني. يجب حفظ نسخة مشفرة خارج الجهاز
والفرع؛ لا يوجد تكامل Google Drive OAuth بعد. تستخدم عملية SQLite snapshot
نسخة مؤقتة غير مشفرة **بمجلد مصدر قاعدة البيانات على جهاز الفرع** لا داخل
مجلد النسخ الخارجي؛ احمِ قرص الخادم بتشفير الجهاز وصلاحيات NTFS محكمة.

### استعادة طارئة

1. أوقف خادم Kasher وكل عمليات الكتابة إليه.
2. احتفظ بنسخة جنائية من الملفات الحالية دون تعديلها.
3. استعد إلى مسار جديد تمامًا لا يحتوي على قاعدة قائمة:

```powershell
python tools/backup_database.py restore D:/KasherPrivateBackups/FILE.kasherbak D:/KasherRecovery/verified.sqlite3
python tools/audit_database.py D:/KasherRecovery/verified.sqlite3
```

4. تحقق من الفواتير الأخيرة والأرصدة ومفاتيح التكرار وملفات WAL، ثم أعد
الخادم للخدمة وفق خطة استعادة معتمدة. لا تستبدل قاعدة البيانات الحية أثناء عمله.

## الوحدات البديلة والكرتونة

في شاشة الأصناف اختر «إضافة وحدة بيع»، أدخل اسم الوحدة وعدد وحدات الأساس
الداخلية وسعرها الخاص وباركودًا اختياريًا. من الكاشير اختر زر الكرتونة بجوار
الصنف، وستُسجل الفاتورة بالسعر المستقل والكمية الفعلية المخزنية.

العمليات المخزنية تستعمل دائمًا عدد الأجزاء الألفية لوحدة الأساس، بينما
البيع بالوحدة البديلة يسجّل إجمالي السطر المالي الأصلي، حتى تُستعاد مبالغ
المرتجعات الجزئية بالقرش الصحيح. يتضمن هذا Tests لبيع كرتونة وإعادة
نصفين ورصيد المخزون والقيود.

**لا تعتبر هذه الميزة جردًا كاملاً للتشغيلات وتواريخ الصلاحية أو تحويل
الوحدات في الشراء والاستلام؛ تلك مهام منفصلة لم تُعتمد.**

## بوابات إطلاق ما زالت مفتوحة

- حماية LAN باستخدام TLS موثوق وآلية إقران للأجهزة بدل HTTP التجريبي.
- مزامنة حقيقية بين الفروع دون تكرار أحداث، ومراجعة تعارض المخزون عند العودة.
- تشغيلات الصلاحية/FEFO وتطبيق الفاقد والجرد الواقعي والميزان المتغير.
- بنية خزائن وأدراج متعددة ووثائق تسوية نقدية ومطابقة المدفوعات.
- طباعة إيصالات 58/80 مم وملصقات وقراءة موازين على موديلات فعلية معروفة.
- ترخيص سنوي بتوقيع رقمي ومفاتيح إصدار تُدار خارج التطبيق.
- متطلبات مصلحة الضرائب المصرية الحالية والتكامل الرسمي/الاعتماد عند اللزوم.
- تثبيت Windows موقع/اختبارات تشغيل ميدانية وAndroid موقّع للإنتاج.
- تشغيل النسخ دوريًا، استعادة دورية خارج الجهاز، ومراقبة الانقطاع والتنبيهات.
- إجراء سيناريوهات القبول الـ34 والاختبارات الأمنية ومطابقة بيانات متجر تجريبي.

**لا تسجل بيانات بطاقة بنكية أو CVV، ولا تستخدم البرنامج في متجر حقيقي
قبل إغلاق بوابات الإصدار وتوثيق الاختبارات.**

## إضافة قيد العمل: التشغيلات والصلاحية

تم تنفيذ مخطط v3 للتشغيلات وسجل حركتها مع FEFO في الشراء والبيع والمرتجعات والتحويلات المحلية والتسويات. يتم رفض بيع المنتهي والكمية غير المدعومة بتشغيلات صالحة، وتُمنع عملية تجهيز الأصناف المتتبعة لحين بناء مسار توريث التشغيلات. تبقى إدارة الاستدعاءات والحجر والإتلاف والجرد المتزامن وتسوية المخزون القديم بلا تاريخ معروف ضمن **بوابات الإنتاج غير المكتملة**؛ لا يصح الادعاء أن إدارة صلاحية الغذاء اكتملت بهذه الإضافة. التفاصيل في [دليل التشغيلات](EXPIRY_LOTS_AR.md).

**تطوير v4:** أُضيف حجز تشغيلات مع سجل أسباب وصلاحية فصل بين الحجز (مسؤول مخزون) وفك الحجز (مدير/مالك). تُستبعد الكمية المحجوزة من FEFO، لكن إدارة سحب المنتجات من السوق والإتلاف الرسمي ما زالا غير مكتملين.

## إقران أجهزة الفرع (مخطط v6)

أضيف إقران أجهزة الكاشير برمز مؤقت أحادي الاستخدام وتخزين سرّ مستقل لكل جهاز في Windows/Android Secure Storage. تتطلب جلسات الشبكة الآن هوية جهاز نشطة وحساب موظف، ويمكن للمدير أو المالك إيقاف الجهاز وإبطال الجلسات. لا تزال شهادة سلامة الأجهزة العتادية، والتوزيع المؤسسي للشهادات والمفاتيح، والمراقبة الأمنية والاختبار الميداني ناقصة. راجع [دليل إقران الأجهزة](DEVICE_PAIRING_AR.md).

## شراء وتوريد بالكرتونة

يدعم قسم المشتريات الآن اختيار وحدة الأساس أو كرتونة/علبة مضافة للصنف، ثم إدخال عدد الكراتين الصحيح وتكلفة شراء الكرتونة مستقلة عن سعر بيعها. يحوّل محرك الخادم الكمية إلى المخزون الأساسي، ويحتفظ بالتكلفة والقروش الأصلية في فاتورة الشراء؛ كما يظل رقم التشغيلة وتاريخ الصلاحية إلزاميين عند استلام الأصناف المتتبعة. وتستمر مرتجعات المورد بالكمية الأساسية على المستند الأصلي. هذه إضافة برمجية واختبارية، وليست اعتمادًا لكل سياسات مشتريات وسجلات الموردين.

## حماية نسخة مشفّرة في وجهة ثانية

أضفت أداة `tools/offsite_backup.py` للتحقق من ملف النسخة المشفّرة في مجلد/مسار تخزين آخر عبر بصمة SHA-256 واستعادة تجريبية إلى مجلد محلي مؤقت، ثم مراجعة الأرصدة المحاسبية قبل تثبيت الملف أو تقليص النسخ القديمة. ويمكن تشغيل النسخ المحلي والنسخ الثاني في أمر واحد باستخدام `--offsite-directory` و`--scratch` من `tools/scheduled_backup.py`. **لا يثبت البرنامج أن الوسيط خارج المبنى، ولا يضبط صلاحيات Windows أو جدول النسخ أو خزنة الأسرار أو التنبيهات تلقائيًا.** يلزم اختبار استعادة مستقل فعلي قبل الإطلاق التجاري. [دليل النسخ المحمي](BACKUP_OFFSITE_AR.md).


## التراخيص السنوية الموقّعة (V9)

أُضيف ترخيص Ed25519 لكل جهاز مقترن، يرتبط بالفرع/المستأجر والجهاز مع فترة لا تتجاوز سنة. يتحقق الخادم من التوقيع على كل عملية كتابة محمية؛ عند الانتهاء أو فقد الترخيص تُمنع العمليات الجديدة وتظل قراءة السجلات ممكنة وفق الأدوار. يبقى مفتاح الإصدار الخاص على جهاز موزع التراخيص فقط، وتُقبل المفاتيح العامة المعتمدة على الخادم. في شبكة الفرع يُفعّل الشرط تلقائيًا، ولجهاز Windows محلي يفعّل الخيار `--license-enforced`. **ملف التشغيل التجريبي لا يفرضه بعد، ولا يوجد تحصيل مالي أو بوابة تجديد تلقائي أو حماية عتادية ضد نسخ الهوية.** [دليل الترخيص](LICENSES_AR.md).


## معاينة وطباعة إيصالات البيع 80 مم

أضفت إيصال بيع عربي محسوب من مستند محفوظ ومُراجع في الخادم، مع طباعة PDF بعرض 80 مم من نظام Windows أو Android وإعادة الطباعة دون تسجيل بيع جديد. ينتمي الإيصال للفرع المسموح فقط، ويحجب تكلفة المخزون وبيانات المستخدم الحساسة، ويرفض أي مبالغ لا تتطابق مع الفاتورة المحفوظة. **هذا مستند بيع داخلي غير معتمد ضريبيًا، ولا يغني عن اختبار طابعة حقيقية أو تنفيذ ESC/POS وأوامر درج النقد والقص.** راجع [دليل الطباعة](PRINTING_AR.md).


## طباعة حرارية مباشرة ESC/POS عبر LAN

تمت إضافة خيار تجريبي لإرسال صورة الإيصال العربي مباشرة إلى طابعة على عنوان IPv4 خاص ومنفذ TCP 9100 مع اختيار 58/80 مم وأمر قص اختياري، دون تعديل الفاتورة المالية أو إرسال مستند غير محفوظ. **لم يتم اختبار أي طابعة حقيقية حتى الآن**، و`GS v 0` قد لا يعمل على الطرازات الحديثة؛ لا يزال USB/Bluetooth وحالة الورق ودرج النقد والامتثال الضريبي غير مكتملين. يجب تأمين شبكة الطابعة نظرًا إلى أن TCP 9100 غير مشفّر. [دليل الطباعة](PRINTING_AR.md).


## حماية تسجيل الدخول من المحاولات المتكررة (ترحيل v10)

أصبحت محاولات الدخول الفاشلة محفوظة في SQLite بطريقة لا تخزن اسم المستخدم
أو كلمة مروره كنص صريح ضمن سجل المحاولات. بعد 8 محاولات فاشلة لنفس هوية
المنشأة/المستخدم خلال 5 دقائق يتم حظر الدخول مؤقتًا، ويستمر الحظر بعد إعادة
تشغيل الخادم. نجاح الدخول يمسح عداد تلك الهوية؛ وبعد انتهاء نافذة الزمن
تبدأ محاولة جديدة. يغطي الاختبار إعادة فتح القاعدة وانتهاء الحظر.

**القيد:** هذه حماية محلية لكل حساب وليست حماية موزعة ضد هجمات عناوين
الشبكة المختلفة أو التخمين المتنقل بين أسماء المستخدمين. لا تزال بوابة
معدلات الطلبات الشبكية، ومراقبة الهجمات، واختبارات اختراق فعلية من نواقص
الإطلاق التجاري.


## تصحيح الربح المحاسبي في لوحة الإدارة

تم تصحيح مجمل الربح والربح التشغيلي التقديري حتى لا تُحتسب ضريبة
القيمة المضافة المحصلة من العميل ضمن إيراد المنشأة. أصبح التقرير يعرض
صافي المبيعات قبل الضريبة وصافي ضريبة المبيعات منفصلين، مع الاحتفاظ
بحقل إجمالي الفواتير شاملًا الضريبة للتوافق مع واجهات API القديمة.
يشمل اختبار الانحدار فاتورة بيع بضرائب ومرتجعًا كاملًا يعكس الضريبة
والتكلفة في الحسابات. هذا تصحيح حسابي داخلي ولا يمثل اعتمادًا ضريبيًا.


## عزل أرصدة العملاء والموردين حسب الفرع — كشف حساب حقيقي

أضيف عرض الرصيد حسب الفرع في شاشة التحصيلات، مع كشف حساب للعميل أو
المورد مستخرج مباشرة من قيود اليومية المعتمدة، ويشمل الفواتير
والمدفوعات والمرتجعات. كشف الحساب يعرض آخر 200 حركة ويحتفظ
برصيد افتتاحي تراكمي للحركات الأقدم.

أُصلح تحقق التحصيل والسداد: لا يمكن سداد دين تابع لفرع آخر اعتمادًا
على إجمالي المنشأة. يتحقق الخادم داخل نفس المعاملة من رصيد الفرع
المحدد وصلاحيات الموظف ومفتاح عدم التكرار. ما زال حد ائتمان العميل
موحدًا على مستوى المنشأة وفق السلوك السابق، بانتظار اعتماد سياسة
الائتمان؛ تخصيص الدفع لفاتورة بعينها والتحويل بين حسابات الفروع
ما زالا بحاجة إلى تنفيذ مستقل. هذا ليس نظام دفاتر ذمم مكتملًا.


## تخصيص التحصيلات للفواتير — ترحيل v11

أُضيف جدول مستقل يربط تسوية الدين بفاتورة واحدة، واختيار الفاتورة
في شاشة التحصيلات. يحتسب الخادم المدفوع عند إصدار الفاتورة والمرتجعات
الآجلة والتسويات المخصصة، ويرفض تجاوز المبلغ المستحق أو الربط
بفاتورة خارج الفرع أو العميل/المورد. معاملة السداد والمحاسبة والربط
واحدة، ومفتاح تكرار الطلب يمنع تحصيل المبلغ مرتين.

حفاظًا على البيانات القديمة، لا تُوزَّع التسويات العامة السابقة
تلقائيًا؛ وجودها يمنع تخصيص دفعات جديدة لهذا الحساب حتى مراجعة
العمليات التاريخية. تدعم النسخة فاتورة واحدة لكل عملية، ولم
تُنفذ تسويات الفائض بعد المرتجعات أو توزيع دفعة على عدة فواتير.
راجع [دليل التخصيص](INVOICE_ALLOCATIONS_AR.md).


## توزيع دفعة واحدة على عدة فواتير — ترحيل v12

أصبحت شاشة التحصيل والسداد تدعم اختيار عدة فواتير وتحديد قيمة
لكل فاتورة في معاملة مالية واحدة. يخزن الخادم تفاصيل التوزيع في
`debt_allocation_lines`، ويمنع اختلاف المجموع عن إجمالي المبلغ،
أو تكرار الفاتورة داخل الدفعة، أو تجاوز مستحق الفاتورة،
أو خلط العملاء والموردين والفروع. يحتفظ النظام بالتوزيعات القديمة
من الإصدار v11 دون إعادة كتابتها.

تعمل حركة النقد والقيود المحاسبية وتفاصيل الفواتير ومفتاح منع
التكرار داخل معاملة SQLite واحدة. أضيف فحص تدقيق مستقل يكتشف
أي اختلاف بين إجمالي الدفعة ومجموع التوزيعات أو عدم تطابق
مالك الفاتورة وحساب السداد.

**لا يوجد توزيع تلقائي على أقدم الفواتير ولا تسوية تاريخية آلية.**
الدفعات السابقة غير المخصصة ما زالت تمنع التخصيص الجديد حتى
تتم مطابقتها بآلية مستقلة وبمراجعة مالية. كما يلزم اختبار ميداني
ومحاسبي مستقل قبل التشغيل التجاري.


## مطابقة المدفوعات القديمة بمديرين مستقلين — schema v13

أضيفت عملية مراجعة يدوية للحركات القديمة المسجلة على حساب
العميل أو المورد بدون تحديد فاتورة. يختار المدير حركة
الدفع الأصلية ويذكر سبب المطابقة، ثم يوزع **كامل المبلغ**
على فاتورة واحدة أو عدة فواتير. لا تُسجَّل حركة نقد
أو قيد يومية جديد. لا يصبح التوزيع فعليًا إلا بعد
اعتماده من مدير/مالك **مختلف عن منشئ الطلب**.

يتحقق الخادم عند إنشاء الطلب وعند الاعتماد من سجل الدفعة
الأصلية وقيودها المتوازنة، وصاحب الفاتورة، والفرع،
والقيمة المتبقية، والمرتجعات. تغيير مستحق الفاتورة
أثناء المراجعة يؤدي لرفض الاعتماد حفاظًا على الحسابات.
إلغاء الطلب يكون بالرفض الموثق، ويمكن بعدها إنشاء
اقتراح جديد. كل خطوة تُسجل في سجل التدقيق.

يبقى التوزيع على الفواتير الجديدة **محجوبًا**
حتى تتم مطابقة **جميع** الدفعات القديمة غير
المخصصة لذلك الحساب. مراجعة المستندات البنكية
ونظام الصلاحيات وصحة قيود العملاء في المتجر
ما زالت مطلوبة قبل الاعتماد التجاري.
راجع [دليل المطابقة](LEGACY_DEBT_RECONCILIATION_AR.md).


## أرصدة المرتجعات واستخدامها على فواتير لاحقة — schema v14

أضيفت معالجة لرصيد العميل أو المورد الناتج عن مرتجع بطريقة
**رصيد على الحساب**. عند اعتماد المرتجع، يخصص النظام منه
أولًا قيمة المستحق المتبقي على الفاتورة الأصلية. أي مبلغ زائد
يبقى في إشعار المرتجع كرصد دائن متاح.

يمكن للمالك أو المدير اختيار إشعار الرصيد وفاتورة أخرى
مستحقة لنفس العميل أو المورد وفي نفس الفرع، ثم إدخال
المبلغ وسبب الاستخدام. يتحقق الخادم من رصيد الإشعار
ومستحق الفاتورة وقت التنفيذ. التطبيق يسجل رابط تخصيص
وتدقيقًا فقط؛ لا ينشئ قبضًا أو صرفًا نقديًا أو قيد
يومية جديدًا، لأن القيد الأصلي للمرتجع موجود بالفعل.

تحديث v14 يرحّل المرتجعات القديمة إلى جدول تخصيصات
صريح، مع الحفاظ على الجزء الذي كان يخفض الفاتورة
الأصلية وترحيل الزيادة كرصيد متاح. كما تعرض لوحة
الإدارة أرصدة العملاء الدائنة وأرصدة الموردين الدائنة
بشكل منفصل عن الديون والمستحقات.

راجع [دليل تشغيل أرصدة المرتجعات](RETURN_CREDIT_APPLICATION_AR.md).


## عهدة أدراج الكاشير المستقلة — ترحيل v15

أُضيفت أدراج نقدية منفصلة على مستوى الفرع، مع وردية مفتوحة
واحدة لكل درج ولكل موظف. يختار الكاشير درجًا شاغرًا ويفتح
وردية باسمه. عندما يُجري بيعًا نقديًا أو تحصيلًا أو رد
نقدية، يربط الخادم **قيد النقدية الفعلي** بوردية
الموظف المصادق عليه. لا تدخل حركة بطاقة أو تحويل بنكي
ضمن النقدية الفعلية للدرج، ولا تدخل حركة موظف آخر
ضمن عهدته.

يحافظ الفرع الحالي على نظام الوردية المشتركة حتى
يُنشئ المالك/المدير أول درج. قبل التبديل يجب إغلاق
الوردية المشتركة وتوثيق العدّ. بعدها يفشل أي تسجيل
نقدي إذا لم يكن لدى الموظف وردية درج مفتوحة؛ لا
يختار النظام درجًا نيابةً عنه.

أضيفت شاشة لإدارة الأدراج والورديات المفتوحة، وسبب
إجباري موثق عندما يغلق المدير وردية موظف آخر.
يظل إغلاق العهدة أعمى: فرق العدّ يظهر بعد الاعتماد
ولا يُحجز كإيراد/مصروف نقدي تلقائيًا. تمت إضافة
فحوص تدقيق لقيود النقد غير المرتبطة بدرج ومطابقة
حسابات الورديات والموظفين.

**المتبقي:** دعم تسليم العهدة بين الموظفين مع عدّ
ثانٍ، وتحويل النقدية بين الأدراج والخزينة الرئيسية،
إيداع البنك، أجهزة درج النقد الحقيقية، موافقات
تسوية الفروق وتقارير محاسبية مطابقة للواقع.
راجع [دليل الأدراج](MULTI_CASH_DRAWERS_AR.md).


## تسليم النقدية بين الأدراج بموظفين مستقلين — v16

أضيف سجل لطلبات نقل النقدية بين درجين مفتوحين في الفرع نفسه.
ينشئ المُرسل طلب نقل موثقًا، ولا يتغير رصيد العهدة إلا بعد
اعتماد **الموظف المستلم نفسه** من حسابه، بعد عدّ المبلغ
فعليًا. يرفض النظام الاعتماد الذاتي، واختلاف الفرع،
والنقل إلى درج مغلق، ومبلغًا يتجاوز النقدية المتوقعة.
يتم فحص رصيد المُرسل مرة أخرى لحظة الاعتماد.

عند الاعتماد يُخصم المبلغ من عهدة المُرسل ويُضاف بالقيمة
نفسها إلى عهدة المستلم. **لا تُعاد كتابة قيد CASH**
لأن النقدية ظلت داخل المنشأة. الطلبات المرفوضة والملغاة
لا تؤثر في عهدة أي طرف، والطلبات المعلقة تمنع إغلاق
الورديات المعنية حتى اتخاذ قرار.

هذه الميزة لا تشمل بعد الخزينة المركزية أو إيداع البنك
أو نقل العهدة بين خوادم فروع مستقلة، ولا تثبت صحة عدّ
النقدية دون محضر تسليم فعلي موقع من الطرفين.
[دليل إجراءات النقل](CASH_DRAWER_TRANSFERS_AR.md).
